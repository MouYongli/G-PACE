# Formalisation: Assumptions, Implementation Checks and Discrepancies

This document accompanies the formal part of the paper (T020). The statements and proofs are in `paper/latex/sections/preliminaries.tex` (main text) and `paper/latex/supplement/` (supplement; build with `make supplement` in `paper/latex/`). Here we record what the paper cannot: which code and tests check each assumption the proofs use, where the plan and the code disagree, and what is proposed. Terms follow plan sections 3.2 to 3.4 and decision D005.

## 3. Discrepancies between plan, documents and code

Each item names what disagrees, which side the formalisation follows, and who would change what. None blocks T020; none changes a reported number.

1. **Derived flag missing from the plan's attribution tuple.** Plan 3.2 writes $a=(u,c,f,\rho,\pi,\gamma,\kappa)$, but plan 3.3's default constraint requires "not derived", and the contract and code carry `derived`. The paper adds $\delta$. Proposal: add $\delta$ to plan 3.2 (plan owner).
2. **Valid end missing from the plan's supersession event.** Plan 3.2 writes $(c,\sigma,\eta)$; the contract (answer to change-sequences open question 2) adds `valid_end`, which sets the effective valid end and so affects `AT(valid=d)` and `end(?c)`. The paper writes $(c,\eta,\varepsilon,\kappa)$. Proposal: add $\varepsilon$ to plan 3.2.
3. **"Four kinds only".** Plan 3.2 says the entries added at a version are of the four kinds only; change sets also carry entity-equivalence entries and a vocabulary label. The plan's vocabulary and entity assumption covers them, and the code invalidates every view on either. Proposal: plan 3.2 says "four kinds of entries, plus equivalence entries and vocabulary changes, which the proposition excludes".
4. **What "matches" means in the proposition.** Plan 3.4's condition "no supersession event points to a claim that matches a claim pattern" is vacuous if matching includes the "currently accepted" negation, because a superseded claim no longer matches. The paper defines matching on positions and the attribution constraint only (state, valid time and filters ignored), as `matching.claim_matches` does. Proposal: say so in plan 3.4.
5. **Exactness conditions incomplete.** Plan 3.4 lists: one positive pattern with local filters, "currently accepted", no selection or aggregation, no new matching claim superseded within $\Delta$, no supersession of an already superseded claim. The proof also needs: no negated pattern (implicit in the plan), no world time (`AT(valid=)` is not in the dependency record), no repeated or scope variable (ignored by the matcher), decidable filters and no `end()` filter; **no new attribution on a claim superseded by r** (an acceptance of a superseded claim triggers but changes nothing, supplement Example 6(iii)); and for the citation level, no evidence link on a superseded claim and no evidence link repeating an identifier already cited for the same answer. The main-text statement now also names current state explicitly (a historical query over-marks on a change event, supplement Example 5). On the fixtures no over-mark occurs; each condition is shown necessary by a constructed case in `tests/integration/test_formalisation.py`. Proposal: replace the plan 3.4 list with the conditions of Proposition 2.
6. **Historical queries and change events.** Plan 3.4 gives "a supersession event of kind change does not alter [a historical query's] result" as an over-approximation. That holds only without world time and without `end()` filters: with `AT(valid=d)`, a change event whose valid end is at or before $d$ removes an open-ended claim (supplement Example 5). Proposal: qualify the example in plan 3.4.
7. **Level of a mark.** Plan 3.4 states exactness as "marked iff answers or witnesses change"; this is right, but the push strategies raise an answer-level mark for every new match, including a second acceptance of an already accepted claim, which changes only the witnesses. So pure push regenerates text for some views that are only citation-stale; hybrid and pull do not (they confirm with fingerprints). Proposal: plan 3.4 and 5.4 say that the claim-pattern decision does not separate the two levels for insertions; E003 can report how often this happens.
8. **Undecidability.** Plan 3.4: "Exact static decision is undecidable in general." True for general queries (Levy and Sagiv), but this fragment is not shown undecidable, and the paper makes no claim about it. Proposal: plan 3.4 says "for general query languages; not claimed for this fragment".
9. **Evidence is one flat set (decided: per answer; resolved in PR #114).** Plan 3.4 defines $\mathrm{ev}$ as one union over all witness claims, and `QueryResult.fingerprints()` hashed that flat set of span identifiers before PR #114. Sentence-level citations are per row, so if a new evidence link on a witness claim cites a span already cited for another answer, a sentence's citations change while $\mathrm{ev}$ does not, and the reference (re-query) reports no staleness. The fixtures show no such case. **User decision 2026-11-26: record evidence per answer.** The paper models $\mathrm{ev}$ per answer ($\mathrm{ev}_t$, supplement S1.4), and the code follows since PR #114: `QueryResult.fingerprints()` hashes each answer with its own evidence, and the flat union `evidence_set()` is no staleness input. Plan 3.4 wording (PR #114 proposal, with the plan owner): "$\mathrm{ev}$ maps each answer to the union of the evidence links, visible at the cut-off version, of the claims in its witnesses"; supplement S1.4 states the same.
10. **`attribution: false` is not sound (decided: option removed; resolved in PR #114).** `configs/views/staleness.yaml` documented an option `attribution` for the claim-pattern strategies. With it off, `matching.triggers` matches only new claims, so a new attribution on an existing claim (an acceptance) that makes a constrained pattern match is no trigger; a scratch replay shows no trigger at version 2 for an endorsing attribution that the default options catch. No configured arm uses the option. Proposal (T019 or views owner): with the constraint off, treat every new attribution on a claim whose positions agree as a trigger, or remove the option (supplement Corollary 3 explains why). **User decision 2026-11-26: remove the option**; removed in PR #114.
11. **Tie-break of the effective valid end.** The contract says "the earliest change supersession stamped $\le r$ that states one" without a tie-break. `GraphState.valid_end` and `Index.valid_end` order same-stamp events by `supersession_id`; `compile.earliest_change_end` by `STR()` of the entry IRI, which percent-encodes the ID. IRIs are built with `quote(id, safe="")`, so an encoded character sorts as `%` (0x25), before digits and letters: for example `s0` precedes `s:2` by ID, but `s%3A2` precedes `s0` by IRI. They can therefore disagree for two change events with valid ends on one claim in one change set. In that case `end(?c)` differs between the matcher and the compiled query, and the matcher can decide a local `end()` filter false at both its before and after evaluations while SPARQL holds it true: **a missed mark (a soundness failure), not only an over-mark.** No fixture has two such events. Proposal (contract owner T014, with T017): fix the tie-break in the contract (for example by entry ID, with the compiler comparing decoded IDs or the store rejecting the case), or forbid two change events with valid ends on one claim in one change set; add a regression test with IDs that reorder under encoding.
12. **Stale open question.** `docs/research/query-ir.md` section 7, open question 3, says the matcher ignores the relaxed defaults. That was fixed: dependency records keep the relaxations and `_satisfies` applies them (`test_marks_ignore_what_the_default_constraint_rejects`). Proposal (T017 document owner): mark it resolved.
13. **Count and latest refinements.** Plan 3.4 excludes aggregation and selection from the exactness conditions. Remarks 1 and 2 of the supplement show that a single-pattern distinct count is exact under the same conditions and that latest-by-version is exact for insertions. Optional: mention in plan 3.4.
14. **Latest-state key and witnesses.** Plan 3.3 says "maximum by version"; the code uses the later of the claim's and the constraining attribution's stamps ("latest confirmed") and keeps every row of the selected claim as its witnesses (`query-ir.md` section 4). The paper follows the code. Proposal: plan 3.3 and 3.4 use this wording.
15. **What a citation-based dependency sees.** Plan 3.4 says such a dependency "sees only the insertions that point at entries the view has already consumed (supersession events)" and misses "insertions that fall inside the scope of a negation or an aggregate, such as an acceptance". The acceptance of the running example is an attribution on a used claim, so it does point at a consumed entry; what the used-claims arm misses is that it is not a supersession event (`citation.py` notes that its `watch_mentions` variant catches it). The paper says "none of the three supersedes anything". Proposal: reword plan 3.4 accordingly.
16. **Join bound.** The proofs hold for any number of joined patterns; the bound of three is a cost limit. No change proposed.
