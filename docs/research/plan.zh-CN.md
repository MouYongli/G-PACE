# GRACE：面向大语言模型智能体的图记忆增强上下文引擎，基于双时间 RDF 上的查询定义视图

Nov 23, 2026 · @Yongli

## 1. 概述

英文题目：GRACE: A Graph Memory–Enhanced Context Engine for LLM Agents with Query-Defined Views over Bitemporal RDF

GRACE 取自 Graph Memory–Enhanced Context Engine（**GR**aph memory–enh**A**nced **C**ontext **E**ngine）。

本计划研究一个问题：智能体的对话历史不断修订时，交给模型阅读的压缩内容何时还能用、何时必须重建，以及为此维护一张图是否划算。方法是在词法加稠密的混合检索之上增加一条结构化图通道，并把经常读取的派生上下文维护为由查询定义的视图。

计划按语义网方向同行评审会议研究论文的评审标准撰写：与语义网的相关性、新颖性、严谨性、评测的设计与执行、可复现性，以及 15 页 LNCS 正文必须自足。计划不绑定某一届的截稿时间。9.3 节划出最小可发表核心，核心结果在阶段 2 结束后先以预印本公开；其余部分在有余力时完成。

### 1.1 上下文是稀缺资源

智能体的交互历史无限增长，而每一步可用的上下文有上限。更大的窗口只能部分缓解：每次调用的计算与费用随输入长度增长；模型对长输入的利用不均匀，相关信息位于输入中段时准确率下降，实际有效的上下文长度常常远短于标称值。所以每一步都重读全部历史既贵，也不保证最准。

### 1.2 现有做法及其失败方式

现有系统用三类办法缩短模型要读的内容。

| 做法 | 怎么做 | 在历史不断修订时怎么失败 |
| --- | --- | --- |
| 压缩 | 把历史或其较早部分改写成一段短文：滚动或递归摘要、分层换入换出、智能体框架内置的自动压缩、token 级提示压缩 | 摘要不记录每句话依赖哪段历史。新消息修订事实后，摘要已经不对，而系统并不知道；唯一安全的补救是全量重写。压缩还是有损的，丢掉的细节无法找回 |
| 检索 | 把历史存在外部，每一步用 BM25 加稠密检索取回几段原文，再融合排序 | 系统的提议和用户的请求在字面与语义上都很接近，排序分不清哪一条决定当前约束。集合、计数、最新状态、过去某时点的状态需要拼合分散的证据，按排名取段落拼不全 |
| 结构化记忆 | 把事实抽成记忆条目、状态表或图，读取时查询 | 多数系统只在单条事实冲突时让旧事实失效，并不知道建立在这些事实上的派生内容是否还对；新说法常常直接覆盖旧说法，不区分是谁说的、算不算数 |

三种失败可以归纳为：派生上下文过期而无信号；归属不清；证据分散。

### 1.3 方法概要

方法由两部分组成。

| 部分 | 内容 | 研究点 |
| --- | --- | --- |
| 图通道 | 只追加、双时间的 RDF 声明图。每条消息被抽取为默认不被断言的声明，带证据片段、说话人归属、交际功能、有效时间与知晓版本。任务被编译成受限的 SPARQL 查询，结果与词法、稠密候选融合 | 角色决定哪条旧声明可以被取代；图通道在哪些题型上带来准确率 |
| 查询定义的视图 | 每个视图由一条查询定义，查询结果被写成逐句带证据的文字（模板序列化或 LLM 渲染），并记录截止版本。新消息写入后，系统按定义查询判断哪些视图过期：答案变了的句子重新生成，只是证据变了的句子由程序补引用，判断不可靠时回退到原文 | 过期的定义与判定；LLM 渲染相对模板序列化是否必要；维护视图何时比每次读取都重算更省 |

系统在实现上分三层：图记忆维护历史，上下文引擎为当前任务组织证据，下游 LLM 生成回答。三层是架构描述，见第 5 节；研究问题按上表的两部分和成本组织。

### 1.4 两个目标与三条主张

系统同时追求两个目标：相对全历史阅读、压缩和混合检索，保持或提高任务准确率；降低端到端 token 开销，写入侧（抽取、校验、视图渲染、失败尝试）与读取侧（规划、作答）的每次 LLM 调用都计入。

核心主张有三条，每条都配有会推翻或收窄它的结果（见第 4 节）：

- **图通道的收益集中在特定题型。** 在归属敏感的状态追踪、聚合、多跳连接和按时点查询上，图通道提高准确率；在单段落查找上打平。计划不主张图优于字段相同的关系表：两者是同一数据模型换了引擎。RDF 在这里是基于标准的载体，它的价值落在开放谓词、标准词表和可互操作性上。
- **过期由定义查询决定。** 只记录“视图用过哪些声明”，能捕到这些声明被取代，但会漏掉三种变化：新增匹配、命中否定条件的非取代写入（例如一次接受）、聚合成员的变化。按定义查询的声明模式做判定不会漏。
- **质量对齐时，维护视图在“修订频繁且同一历史被多次读取”的区间更省。** 这个区间之外，全历史或查询时解决更合适，计划会报告不占优的区域。这条主张有一个前提：LLM 渲染的视图比查询结果的模板序列化更利于 reader。前提不成立时，没有昂贵的产物需要缓存，这条主张不成立。

计划同时接受否定结果，并把两种结局当作主要情形来准备。第一，模板序列化的事实卡与 LLM 渲染的视图同样好用：此时每次读取重跑查询即可，论文讲“过期判据加查询时现算”。第二，读取时重新执行查询就能同样准确地判定过期：结论收窄为“精确的新鲜度检查很便宜，瓶颈在抽取与渲染”。已有预印本的数据表明第二种结局有相当的可能。

## 2. 背景与相关工作

来源可回溯、双时间、角色区分、沿依赖边的级联失效、按三元组模式的缓存失效都已有先例。把派生记忆看作演化数据上的视图，也已出现在 2026 年的两篇预印本里。本计划的空缺因此限定为：由定义查询导出的、细于整源刷新的失效条件（这一粒度是否新，待阶段 0 核对），它在只追加双时间 RDF 图上的形式化判据，以及在自然对话上带完整 token 账本的评测。

2026 年的预印本大多未经同行评审。做过定向阅读的条目，阅读深度在 11.3 节标注；未标注的条目尚未做定向阅读，引用其具体结论前须读原文；过去两个月内至少出现了五篇相关预印本，定稿前须重新检索。Martin 等（2010）尚未读到原文，MemShift 的附录和 Tether 的后三分之二尚未读完，2.1 节与 3.4 节中依赖它们的表述是暂定的，读完原文是阶段 0 的工作（第 9 节）。

### 2.1 近邻工作与本计划的差别

| 方向 | 近邻工作已经做到的 | 本计划的差别 |
| --- | --- | --- |
| 时序图记忆 | Zep/Graphiti：边带两条时间线，可回溯到 episode；LLM 判定冲突后使旧边失效；新增节点时更新社区摘要，靠周期性全量刷新纠偏 | 按角色决定是否允许取代；失效对象是派生视图，并有明确的有效性判据 |
| 追加式存储加查询时解决 | APEX-MEM：以实体为中心的属性图，事实挂在带日期的事件上，读取时处理冲突，不缓存 | 持久化视图并维护其新鲜度；把“不缓存、每次查询时解决”作为成本上最直接的对手 |
| 程序化状态记忆 | ProgMem：把对话事件编译为状态更新程序并校验证据；用 Qwen3-4B/8B/14B 在 LoCoMo 的 1,540 题上评测 | 由查询定义的视图及其重建；证据召回与成本对照 |
| 派生记忆的级联失效 | PACMI：依赖边由标注给出，仅同槽位单值替换触发失效，新增集合成员不触发。MemoRepair：事件只有删除、更正、迁移，没有插入。MemTX：沿派生关系图回滚，自述只覆盖已记录的来源。Kumiho：沿依赖边做影响分析，由智能体显式调用。Tether（Dependency-Tethered Memory）：核验结论记录它所依据的对象版本，读取时沿依赖边撤回；同一对象出现更高版本时触发撤回，集合与计数变化没有对应机制 | 这些工作的依赖都指向派生物已经消费的记录或版本。本计划的依赖是定义查询的模式，能捕捉从未被消费过的新记录 |
| 派生记忆即视图的诊断 | MemShift：实测由引用构成的依赖键在来源修订后漏掉 16.9% 的已变化条目，在重新定义后漏掉 32.4%，并把原因对应到谓词锁的幻读问题；粗粒度的来源键不漏，但让 99% 以上未变化的条目失效；另设定义作用域键、金标键和“不存储、查询时现算”的对照。MemDerive：一个基准，把派生状态表述为数据库表上的视图，金标用带聚合的 Datalog，见证用最小 why-provenance；测得记忆系统刷新了 82.4% 的显式变更，只刷新了 41.1% 的隐式变更 | 两者都在模板合成数据上，都不是 RDF 或 SPARQL。MemShift 的定义作用域键可能与本计划的声明模式级依赖是同一粒度，其确切定义在附录中，尚未读完。若两者相同，本计划不声称粒度上的新意，差别限定为：在只追加双时间 RDF 图上的形式化、答案与引用两级过期、在自然对话和带噪声的抽取图上的评测。这是全计划最大的新颖性风险，排在所有工作之前核对（阶段 0） |
| 查询缓存失效 | Martin、Unbehauen 与 Auer 的 SPARQL 查询缓存（2010）：与查询模式匹配的三元组发生变化时，使缓存结果失效。Williams 与 Weaver（2011）：按索引的最后更新时间做 HTTP 缓存校验，接近谓词级。Incremunica：SPARQL 结果的增量维护，已支持 FILTER NOT EXISTS、MINUS、GROUP BY 与 ORDER BY | 本计划采用按模式匹配的失效规则，不声称提出它。被缓存的是逐句带证据、有双时间作用域的阅读视图；过期分答案与引用两级；只需要过期判定而不需要增量结果，因为昂贵的是 LLM 重新渲染 |
| 读时复核 | GroundedCache：读取时重新检索，比较块哈希的重合度是否过阈值 | 它比较的是向量检索的 top-k。本计划对确定性查询比较精确的答案、见证与证据指纹 |
| RDF 对话记忆 | Leolani/GRaSP：声明、提及、逐说话人的归属（极性、确定性）。An 与 Gentile：RDF 加 PROV-O，由 LLM 直接写 SPARQL | 更新处理、类型化中间表示、带范围说明的空结果、构造时返回证据集 |
| 角色区分 | TripPy 的 system-inform memory；ParsingDST 的 User/System 分表。MemIR 提出“来源角色坍缩”；一项研究报告多会话共用存储时同名说话人的事实混入率为 0.543 | 已有证据只支持“谁说的很重要”。把交际功能用作“哪条旧声明可以被取代”的守卫条件，其作用须由本计划自己举证 |
| 动态词表 | EDC、AutoSchemaKG、DIAL-KG：关系规范化、schema 归纳与增量演化，均面向文档 | 在对话上、用小模型检验受约束的局部扩展是否值得 |
| 成本评测 | Pollertlam 与 Kornsuwannawit：带缓存折扣的回本分析。统一评测研究：按题分摊建库与查询 token。APEX-MEM、ProgMem、LightMem、MemTX、MemShift、MemDerive 都报告了写入侧 token | 写入侧成本已常有报告。本计划的增量是：质量对齐的比较、含失败尝试的每正确答案成本、更新之下的维护成本 |
| 受控修订基准 | StateMemBench 的反更新探针；另一项工作的受控修订生成器；STALE 的“前提抵抗”探针 | 这些基准没有双时间成对问题，也没有逐消息的视图失效真值 |

### 2.2 已知的不利证据

这些结果决定了评测该防什么，计划不回避它们。不同论文的分数因骨干模型和判分方式不同，不可直接比较。

- **全历史基线很强。** Mem0 自己的表里，GPT-4o-mini 读全文在 LoCoMo 上的 LLM 判分准确率是 72.90，高于其图变体的 68.44（后一个数字待复核）。
- **小规模下图结构收益很小。** 相同抽取器下，Llama-3.1-8B 在 LongMemEval-S 上平面记忆与图记忆的问答准确率是 0.614 对 0.620（Does Memory Need Graphs?）。
- **LLM 直接写 SPARQL 不可靠。** An 与 Gentile 的系统准确率在 11% 到 15.6% 之间，同文的全上下文基线在 LongMemEval-S 上是 0.326，作者把 NL-to-SPARQL 列为主要瓶颈。这支持本计划用受限中间表示加确定性编译。
- **小模型的结构化写入是弱点。** 一项对比研究中，Nemori 的格式错误率从 gpt-4o-mini 的 17.91% 升到 Qwen-2.5-3B 的 30.38%。HaluMem 报告多数系统漏掉一半以上应做的更新。
- **读取时现算可能就够了。** MemShift 的“查询时视图”一臂每次查询只多花 246 个 reader token，写入侧每个世界 5.67 万 token；而存储方案是 31.97 万摄取加 130 万维护。本计划的视图由确定性查询定义，读取时重新执行并比较指纹不花 LLM token。计划把它列为正式实验臂，并作为消融 A 的精确参照（7.3 节）。
- **检测的收益以修复能力为上限。** MemShift 报告，开放权重的小模型写入器至多正确重推导 25% 的已变化条目，而精确重算至少 91%。本计划的视图内容由确定性查询给出，LLM 只负责渲染，这一设计选择单独检验；同一项消融还检验连 LLM 渲染都不用的模板序列化（消融 C）。
- **小模型分数的参照并不稳定。** Qwen3-8B 读全文在 LoCoMo 上的 LLM 判分准确率，两篇预印本分别报 50.83 与 71.10（后一个数字只读到摘要层面，待复核）。所以回答提示与判分器必须固定并披露，不引用他人的基线数字作对比。

### 2.3 理论基础

- **无关更新与查询—更新独立性。** Blakeley、Coburn 与 Larson 对选择、投影、连接视图给出了无关更新的充要条件，并指出“不是无关的更新未必影响派生关系”。Levy 与 Sagiv 指出独立性一般不可判定，以查询可达性为充分条件，并指出前者的充要条件只适用于没有重复谓词的合取查询。任何含两个以上模式的基本图模式在三元组表的视角下都是自连接，所以精确性不能照搬到 RDF。
- **增量视图维护。** Gupta 与 Mumick 的综述；Motik 等对带分层否定的 Datalog 物化维护给出带正确性定理的算法；DBSP 给出一般的增量化方法；Incremunica 在 SPARQL 引擎中实现了非单调算子的增量求值。
- **单调性。** 良设计的 SPARQL 模式是弱单调的，弱单调性的语义判定不可判定（Arenas 与 Ugarte）。本计划的查询片段含否定、计数与最新状态选择，不在弱单调片段内，所以采用保守的语法检验。
- **来源。** 见证取 why-provenance，即最小见证的集合；how-provenance 的半环框架及其对非单调查询的扩展（spm-semiring、SPARQLprov）和对聚合的扩展（半模）作为背景。SPARQLprov 不含聚合函数。
- **版本化 RDF。** BEAR 把查询分为版本物化、增量物化与版本查询。按这套词汇，截止版本上的读取是版本物化查询，过期判定是一个布尔的增量物化查询。双时间 RDF 有 BiTRDF、Bi-VAKs 等模型，没有标准词表。
- **依赖追踪与视图选择。** Doyle 的真值维护系统、Adapton；“哪些视图值得持久化”引用 Agrawal 等人的视图选择工作。

## 3. 问题形式化

本节给出记号、过期的定义、一个观察和一个命题。正文中这一部分约占一页；完整证明、片段假设清单和判定策略的细化放入补充材料。

### 3.1 历史、版本与读取

输入是一条按时间到达的对话历史，系统在任意时刻都要能用当时可见的记忆回答问题或输出状态，并给出所依据的原始消息。

$$
\mathcal H=\langle h_1,\dots,h_N\rangle,\qquad
\mathcal M_r=\mathrm{Write}(\mathcal M_{r-1},h_r),\qquad
(g,R)=\mathrm{Read}(\mathcal M_r,q)
$$

| 记号 | 含义 | 在实验中的作用 |
| --- | --- | --- |
| $h_t$ | 第 $t$ 条消息，带说话人、原始 ID 和可得的时间元数据 | 原文日志的单位；证据按原始消息 ID 对齐 |
| $\mathcal H$ | 完整历史；$L(\mathcal H)$ 是其序列化后的 token 数 | 全历史基线与记忆系统接收相同信息 |
| $\mathcal M_r$ | 读完第 $r$ 条消息后的记忆：原文日志、文本索引、声明图 $G_r$、若干视图 | 每条消息提交一个版本；读取只看指定版本 |
| $q$ | 到达于版本 $r$ 的一次读取任务：一道问答题或一次状态请求 | 参考答案 $a$ 与标注证据 $e$ 由评测器保管 |
| $g$, $R$ | 系统输出的答案；实际呈给 reader 的证据消息 ID 集合 | 答案质量与证据质量分开计 |
| $W$, $U$, $A$ | 写入、读取中间步骤、最终作答各自的 LLM token | 成本账本，见第 8 节 |

问题的世界时间与快照截止版本分别指定。“当时知道什么”和“现在回看当时是什么”是两个不同的读取。

**读取点**是一个（版本，读取任务）对。读取点放在哪里，决定了一个基准能检验哪些主张，见 6.1 节。

### 3.2 声明图与双时间

声明图在抽象层面由四类条目组成，每一类都带版本戳。

- **声明** $c=(s,p,o,\omega,\tau,\kappa)$：主语、谓词、对象、作用域、有效时间或区间、知晓版本 $\kappa(c)$。知晓版本是首次产生它的消息的版本号。声明是命题本身，不含“谁说的”。
- **归属** $a=(u,c,f,\rho,\pi,\kappa)$：说话人 $u$ 对声明 $c$ 的一次表态，带交际功能 $f$（请求、提议、接受、拒绝、确认、告知等）、转述方式 $\rho$、极性 $\pi$ 和知晓版本。本计划所说的角色，就是归属上的 $(u,f)$。
- **证据链接** $(c,m,\kappa)$：声明 $c$ 由消息片段 $m$ 支持，自版本 $\kappa$ 起可见。
- **取代事件** $(c,\sigma)$：声明 $c$ 自版本 $\sigma$ 起不再是当前被接受的状态。

图只追加：$G_r\subseteq G_{r+1}$。版本 $r+1$ 新增的条目只能是这四类，版本戳都是 $r+1$。因此 $G_{r_0}$ 中出现的所有版本戳都不大于 $r_0$，而 $G_r\setminus G_{r_0}$ 中的所有版本戳都大于 $r_0$。

同一命题被再次提及时不产生新声明，只新增一条归属和一条证据链接。一方提议、另一方接受，是同一条声明上的两条归属。

**词表与实体标识的假设。** 本节的结果假设：在视图的截止版本与读取版本之间，词表（谓词、别名、排他规则）和实体标识不变。词表版本改变或两个实体被合并时，查询要重新编译，声明模式的匹配关系随之改变，这不属于上面四类条目。系统对此取最保守的处理：该历史的全部视图失效（5.2 节）。这类事件的次数和由此产生的重建成本单独报告。

有效时间 $\tau$ 描述事实在世界上何时成立，知晓版本与取代版本描述系统何时知道。两条时间线独立。

### 3.3 查询片段

视图与读取使用同一个受限查询片段。查询的原子是**声明模式** $(s,p,o,\omega)[u,f]$。前四个位置匹配声明，可以是常量或变量。方括号中的归属约束可选，要求该声明上存在说话人为 $u$、交际功能为 $f$ 的归属。带归属约束的模式既可能被新声明匹配，也可能被已有声明上的新归属匹配。

片段允许六类操作：

- 过滤（对常量和有效时间的比较）；
- 一到三个声明模式的连接；
- 否定：一个与正的部分共享变量的声明模式上的 NOT EXISTS，不嵌套；
- 去重计数；
- 最新已确认状态的选择（按版本或有效时间取最大者）；
- 来源展开（投影出答案所依据的声明与证据）。

“当前被接受”是一种内置的否定：声明匹配，且不存在版本不大于截止版本的取代事件。当前状态查询带它，历史查询不带。一般否定用于“提议过但尚未被接受的候选”这类查询：正的部分是带提议归属的模式，否定部分是同一声明上带接受或拒绝归属的模式。

片段不含属性路径，默认图固定，采用简单蕴涵。过滤只与常量和声明自带的有效时间比较，不允许与读取时刻比较（如“最近一周”），因为那样的视图不经任何写入也会过期。含相对时间的任务在编译时换算为绝对区间，只作为答题期的临时查询，不持久化为视图。

查询以截止版本为参数，记作 $Q[r]$：它只看版本戳不大于 $r$ 的条目。版本 $r$ 上的读取求值 $Q[r]$ 于 $G_r$。

**时间旅行稳定性。** 对任意 $r\ge r_0$，$Q[r_0]$ 在 $G_r$ 上的结果等于它在 $G_{r_0}$ 上的结果，因为之后追加的条目版本戳都大于 $r_0$，被参数过滤掉。所以过去某一版本的读取永不过期；过期只可能发生在截止版本随时间前移的读取上。这一结论同样依赖 3.2 节的词表与实体标识假设。

### 3.4 视图与过期

**视图**由六项组成：查询模板 $Q$ 及其绑定参数、截止版本 $r_0$、逐句带证据的文本、所用声明与归属（见证）、所引证据、依赖模式。

**答案、见证与证据。** $\mathrm{ans}(Q[r],G_r)$ 是答案集。每个答案的见证 $\mathrm{wit}$ 按如下约定定义：

- 正的连接部分取 why-provenance：使该答案成立的全部最小见证。每个最小见证是一个由声明和满足归属约束的归属组成的集合；一个答案可以有多个最小见证。
- 否定条件没有见证，答案的见证只来自正的部分。
- 去重计数的见证是被计入的各成员的见证之并。
- 最新状态选择的见证是被选中答案的见证。

$\mathrm{ev}$ 是见证中各声明在截止版本可见的证据链接之并。

**定义（两级过期）。** 截止版本为 $r_0$ 的视图在版本 $r\ge r_0$：

- **答案过期**，当且仅当 $\mathrm{ans}(Q[r],G_r)\neq\mathrm{ans}(Q[r_0],G_{r_0})$；
- **引用过期**，当且仅当答案未变，而 $(\mathrm{wit},\mathrm{ev})(Q[r],G_r)\neq(\mathrm{wit},\mathrm{ev})(Q[r_0],G_{r_0})$。

分两级是因为修复代价不同。答案过期时，文本内容必须重新生成。引用过期时内容没变，只是逐句的引用不完整了。最常见的情形是同一事实被再次提及：声明集合不变，只多一条证据链接，自然对话里这种重复很多。文本的每一句都绑定到结果行（5.4 节），所以引用过期由程序补上引用，不调用 LLM。

空结果和计数所附的范围说明（“在截至版本 $r$ 的观察范围内”）不属于视图内容。它由程序在读取时按当前版本生成，不进入过期定义；否则每次写入都会让这类视图过期。

**观察（只看见证不充分）。** 只在视图所用声明被取代时才失效的策略，能捕到“所用声明被取代”，因为取代事件指向的正是视图用过的声明。它漏掉三种变化：

- 新增匹配：视图“Lina 负责哪些服务”原有一个答案 Atlas；新声明“Lina 维护 Boreal”写入，原声明未动，答案集多了一个成员。
- 非取代写入命中否定条件：视图“提议过但尚未被接受的候选班次”原有 TR7143；用户接受 TR7143 是该声明上的一条新归属，没有取代任何声明，但它命中否定条件，答案消失。
- 聚合成员变化：视图“已提到的乐器数”原为 1；新增一条乐器声明，计数变为 2。

第一种情况已有实测数据（MemShift）。后两种可以由一个更强的引用式策略捕到：在所用声明之外，再监听否定与聚合部分的声明模式。这个更强的策略仍然漏掉非聚合视图的新增匹配。评测把它列为单独一臂（5.4 节），以免把引用式基线比弱了。

一般地说：只追加的图上，一切变化都是插入。引用式依赖只看得到指向已消费条目的插入（取代事件），看不到落在否定或聚合作用域内的插入，例如一次接受或一个新成员。所以在这种存储上，由已消费条目之外的插入引起的失效是常态，不是边角情形。

**命题（可靠性）。** 设 $\Delta=G_r\setminus G_{r_0}$，且词表与实体标识在 $r_0$ 到 $r$ 之间不变。如果 $\Delta$ 中

- 没有新声明或新归属与 $Q$ 的任何声明模式匹配（包括否定条件和聚合内部的模式），并且
- 没有取代事件指向与 $Q$ 的某个声明模式匹配的声明，

则视图在版本 $r$ 未发生答案过期，见证也未变。若 $\Delta$ 中还没有证据链接指向与 $Q$ 的正模式匹配的声明，则视图也未发生引用过期。

证明思路：对查询代数做结构归纳。在所设条件下，各声明模式在 $G_r$ 与 $G_{r_0}$ 上的匹配相同；$Q[r]$ 与 $Q[r_0]$ 只差版本上界，而 $G_{r_0}$ 中的版本戳都不大于 $r_0$，两个上界接受相同的条目。这个命题是查询—更新独立性的一个实例，对应的缓存失效规则出自 Martin 等；对否定和聚合由组合性成立，正文给出短证明。Martin 等的确切规则尚待对照原文（阶段 0），这一段的措辞在此之前是暂定的。

**匹配单位（实现说明）。** 用 RDF 1.1 标准具体化时，一条声明被编码为一组三元组（主语、谓词、对象、知晓版本各一条）。如果逐三元组模式匹配，每条新声明都带一条知晓版本三元组，会与任何查询中的同类模式匹配，判定退化为“任何写入都失效”。所以匹配在声明模式（一个具体化星形）上进行。用 RDF 1.2 的三元组项时一条声明对应一个项，这个问题不出现。这是一条实现说明，不作为贡献。

**精确性与界限。**

- 判定在下列条件同时成立时精确，即标脏当且仅当答案或见证发生变化：查询只有一个正的声明模式，可带局部过滤；含“当前被接受”否定；没有选择算子和聚合；$\Delta$ 中匹配的新声明没有在 $\Delta$ 内又被取代；取代事件指向的声明在 $r_0$ 时尚未被取代。
- 条件之外会过度近似。三个例子：带最新状态选择时，新写入一条有效时间更早的匹配声明，答案与见证都不变；历史查询不含“当前被接受”否定，取代事件不改变结果；已被取代的声明再次被取代。
- 连接会过度近似：新声明匹配了一个模式，但没有连接伙伴。否定条件中的模式也会过度近似：命中的条目并不对应任何当前答案。
- 实例级的精确判定等价于增量求值或重新求值；带答案、见证与证据指纹的读时重查就是精确的参照方法。一般情形下的静态精确判定不可判定。

**判定策略的阶梯。** 谓词级 ⊇ 声明模式级 ⊇ 声明模式加局部过滤 ⊇ 读时重查。阶梯上的每一级都不漏报，越往后过度标脏越少、每次检验的代价越高。各级在对话负载上的误报率由实验测量。两种引用式策略（仅已用声明、已用声明加否定与聚合模式）会漏报，不在阶梯上。

**不声称的内容。** 新的失效算法；SPARQL 缓存失效的首个可靠性结果；复杂度结果；增量维护算法；“基于来源的失效一般而言不正确”（在单调查询下，它对删除是正确的）。声明模式级这一依赖粒度本身是否新，取决于它与 MemShift 定义作用域键的关系，在阶段 0 核对之前不声称。

### 3.5 三个贯穿全文的例子

**多值谓词不应被“最新值”覆盖（新增答案）。** LoCoMo 的 conv-26 中，Melanie 在 D2:5（2023-05-25）提到拉小提琴，在 D15:26（2023-08-28）提到吹单簧管。测试题问她会哪些乐器，参考答案是两者都算。写入器生成两条带来源的 `playsInstrument` 声明；第二条写入时，第一条完全没变，但“Melanie 会的乐器”这个视图已经过期。只保留最新一条边，或只监听已用过的声明，都会答漏。如果 Melanie 之后再次提到拉小提琴，声明集合不变，只多一条证据链接：视图只发生引用过期，程序补上引用即可。

**提议不应覆盖请求（归属）。** MultiWOZ 的 SNG0296.json 中，turn 0 用户要求最晚 20:45 抵达；turn 5 系统提议 TR7143（19:48 发、20:38 到）；turn 6 用户接受并索要预订号。“最初的到达要求”始终是 20:45，“当前选择”在 turn 6 之后才是 TR7143。MultiWOZ 2.2 的标注在这里把 `train-arriveby` 改记为 20:38，2.4 保持 20:45；两个版本在“系统提议的值是否写入状态”上的一般惯例，在阶段 1 从数据上核实（6.5 节）。

**确认使候选消失（非单调）。** 同一段对话中，turn 5 之后“等待确认的候选”视图的答案是 TR7143。turn 6 的接受是一条新归属（用户，接受），挂在 turn 5 的提议所引入的那条声明上；没有任何声明被修改或取代。但它使该视图的答案变为空，同时使“当前选择”视图由空变为 TR7143。两个视图都必须重建，而它们所用的声明一条都没有被取代。

## 4. 贡献点与研究问题

新意集中在视图的过期判据、图通道的受控评测和成本评测；声明模型的多数元素是对既有做法的有理由的组合。

### 4.1 贡献点

1. **声明与证据模型。** 基于标准词表的只追加、双时间 RDF 声明图。声明默认不被断言，只有“当前被接受的状态”进入派生图。角色记在归属上：交际功能（请求、提议、接受、确认、告知）与转述归属分作两轴，并被用作取代规则的守卫条件。RDF 的作用是基于标准的载体（PROV-O、SHACL、OWL-Time、RDF 1.2 reifier），计划不主张它优于字段相同的关系表。
2. **查询定义的视图及其过期判据。** 过期分答案与引用两级，引用过期不需要 LLM；指出引用式依赖漏掉哪三种变化，以及它们在只追加图上都是落在视图已消费条目之外的插入；给出覆盖声明、归属、证据和取代四类写入的声明模式级可靠性命题和精确性条件；在对话负载上比较八种判定策略，其中“无 LLM 的读时重查加指纹”和“推送过滤加读时确认”两臂在已检索到的智能体记忆失效文献中未见评测；测量自然对话中各类过期出现的频率。
3. **从任务到工作上下文的可核验路径。** 类型化中间表示到 SPARQL 片段的确定性编译器，构造时投影证据集并为空结果和计数注明证据范围；图结果与词法、稠密候选融合；按证据需求在预算内组装原句与事实卡。
4. **质量对齐的端到端成本与分层诊断。** 模板序列化、LLM 渲染与 LLM 重写三种视图内容来源的对照，它决定缓存视图是否必要；缓存调整后的回本曲线，以及随修订密度和读取次数变化的维护成本面；含失败尝试的每正确答案成本；按变更类型分层的过期判定评测，判定漏报与抽取导致的漏报分开计；金标图与抽取图两种条件的对照；对抽取图本身的直接评估。

来源链接、双时间、请求与提议分开、按模式匹配的缓存失效规则、局部修复都写作“采用的既有做法”，不单独声称新意。

RQ3 的对手有四类：全历史阅读（有无前缀缓存）；压缩（每次更新后重写的滚动摘要，以及不重写、沿用旧摘要）；混合检索、固定槽位表、只追加且查询时解决冲突的无视图记忆；本系统自身的模板序列化变体（每次读取重跑查询，不渲染、不缓存）。变量是每条历史的读取次数、修订密度和上下文预算。每个区间报告回本读取次数，并标出不占优的区间。

| C1 | 检索通道（词法、稠密、结构化），逐一去掉 | 各路有唯一贡献：编号、数字、长尾实体靠词法；改写与指代靠稠密；连接、计数、时点靠图 | 去掉某一路后各切片无差别 | D |
| C2 | 融合方法（RRF、加权） | RRF 足够 | 加权融合明显更好，主配置随之更换 | H |
| C3 | 路由（始终三路、规则） | 规则路由在质量相当时降低每次读取的开销 | 始终三路同样便宜，或规则路由掉点 | H |
| C4 | 按证据需求组装，对比按排名截断 | 同一 token 预算下提高证据完整命中率，降低无依据作答率 | 等预算的融合 top-k 达到相同效果 | E |
| C5 | 词表演化，对比冻结词表加别名 | 在未见关系表达和领域词义歧义上，受约束的局部扩展提高谓词对齐和查询正确率 | 冻结词表加别名同样有效且更便宜；或 schema 膨胀抵消收益 | F |
| C6 | 写入器规模与 LLM 角色的调用方式 | 大写入器恢复抽取图下损失的部分收益；条件触发的角色调用优于固定调用 | 收益只来自多采样 | G |

## 5. 系统设计

系统在实现上分三层：图记忆、上下文引擎、下游 LLM。写入只经过图记忆层，读取自上而下穿过三层；层间只通过带版本号和证据 ID 的接口交换数据。

### 5.1 组件与数据流

| 层 | 组件 | 输入与持久状态 | 输出 |
| --- | --- | --- | --- |
| 图记忆 | 消息日志 | 原始消息、说话人、消息 ID、接收序号、可用时间戳 | 追加写入；每条消息提交一个版本；重试幂等 |
| 图记忆 | 文本索引 | 每条消息及其片段 | BM25 适配实体名、数字、编号；稠密索引适配指代与改写 |
| 图记忆 | 声明图 | 实体、事件、声明、归属、证据片段 | 按实体、谓词、事件、有效期和版本索引；只断言当前被接受的状态 |
| 上下文引擎 | 查询规划与编译 | 当前任务、相关词表片段、时间与来源要求 | 类型化中间表示、SPARQL、匹配到的声明与证据集 |
| 上下文引擎 | 视图存储 | 查询、带行绑定的文本、所用声明、所引证据、依赖模式、截止版本 | 可复用的带证据文字；答案过期与引用过期标记 |
| 上下文引擎 | 检索、融合与组装 | 三路候选、现存视图、token 预算 | 工作上下文：任务、近期原文、已核验状态、证据片段、未决项，附各项计费 |
| 下游 LLM | Reader 与控制器 | 工作上下文、输出契约 | 回答、状态、一次补充检索请求，或“未知” |

写入路径：

1. 原文追加入日志，建 BM25 与稠密索引。
2. 写入器抽取带片段锚点的声明补丁。
3. 程序做结构校验，按角色和排他规则决定追加、取代或并列。
4. 图事务提交，产生变更集（新声明、新归属、新证据链接与取代事件）。
5. 按变更集标记受影响的视图，发布新版本。

读取路径：

1. 任务解析为中间表示，列出必填变量或证据需求。
2. 执行图查询与文本检索，先绑定历史标识与可读版本。
3. 检查常驻视图是否可用：答案过期时重新生成变化的句子，引用过期时由程序补引用，判定不可靠时回退到原文。
4. 在预算内组装工作上下文。
5. Reader 作答，记录所用证据 ID 与真实 token 用量。

图写入失败时，读取可以使用已提交的文本索引，并显式标注覆盖范围；写入从日志重试后原子发布新版本。索引尚未完成时，不得把“查不到”当作“不存在”。

### 5.2 图记忆层

图记忆层只追加、不删除：原文永远保留，声明的取代表现为取代事件的写入，任何过去时刻的状态都能重新读出。

**一条消息可产生的对象**

- **Episode** 保留原文。每个提及指向实体，每条证据指向具体片段、说话人和声明。
- **声明（Claim）** 是一个命题：事件或主语、谓词、对象、作用域、有效时间或区间、知晓版本。两条消息说同一件事时合并为一个声明节点，保留两条证据。消息重试不增加来源数。
- **归属（Attribution）** 连接说话人与声明，携带交际功能、极性和确定性。系统提议一个班次、用户接受它，是同一条声明上的两条归属。两位说话人对同一命题立场相反时，各有一个归属节点；否认不产生第二条声明，立场改变是新增归属而不是覆盖。
- **时间表达** 区分三种：消息的先后顺序、来源报告的世界时间、问题要求的参考时间。没有自然日期时只保留顺序，不编造绝对日期；有“上周”时保存原短语和可得的时间锚点。

这些对象与 3.2 节的四类条目一一对应：声明、归属、证据链接各自带知晓版本，取代事件带取代版本。写入只追加这四类条目，所以每一次写入都落在可靠性命题的覆盖范围内。

**角色分两轴。** 交际功能轴取值为请求、提议、接受、拒绝、确认、告知、承诺、疑问，对应 ISO 24617-2 的对话行为清单。转述归属轴取值为本人陈述、引述他人、假设。两条轴分开标注：一句“他说他想订周六的车”既是告知，又是引述他人的请求。

**词表映射**（具体属性名落地前须对照各规范核对）

| 模型元素 | 采用的词表或做法 | 说明 |
| --- | --- | --- |
| 声明节点 | RDF 1.2 的 reifier（`rdf:reifies`），附 RDF 1.1 标准具体化的等价序列化 | 被指向的三元组默认不被断言，正好表达请求、提议、引述、假设。RDF 1.2 处于候选推荐阶段，引擎支持不齐，所以保留回退 |
| 归属与立场 | GRaSP 式的归属节点，`prov:wasAttributedTo` 指向说话人 | 极性与确定性挂在归属上，不挂在声明上 |
| 交际功能 | ISO 24617-2 的交际功能，建成 SKOS 概念表 | 未找到官方 RDF 版本，需自建概念表并注明对应 |
| 任务状态 | schema.org 的 Action 与预订状态；用户约束（如“最晚 20:45 到”）用本地属性 | 提议是待定的预订，接受后转为已确认；约束始终属于请求 |
| 来源 | PROV-O，含抽取所用模型与提示版本 | 助手复述标为派生来源，不计作独立支持 |
| 片段锚点 | NIF 或 Web Annotation 的选择器 | 证据指向消息内的字符区间 |
| 有效时间 | OWL-Time；区间左闭右开 | 无日期时用消息序号作序数位置 |
| 知晓时间 | PROV 的生成与失效时间，映射到版本号 | 双时间没有 W3C 标准词表，这是本计划自己的映射；读取方式按 RDF 归档的版本物化描述 |
| 结构校验 | SHACL 形状，只校验本次补丁涉及的声明 | 区分 domain/range 推理、结构约束和领域排他规则 |

**变化类型与更新操作**

| 消息类型 | 图上处理 | 读取效果 |
| --- | --- | --- |
| 相同事实再次确认 | 同一声明追加归属与证据链接；助手复述标明派生来源 | 可按来源检索；复述不增加独立支持；相关视图只发生引用过期 |
| 真实状态变更 | 同一主体、角色、作用域且有排他规则时，写入取代事件并新增声明 | 可查当前状态与旧时状态 |
| 迟到更正 | 追加更正，记录被修订的目标和适用的过去区间；旧的知晓快照仍可读 | “昨天当时所知”与“今天回看昨天”可以不同 |
| 请求、提议、接受 | 分别建归属，只推进对应的任务状态；提议不关闭请求的约束 | 可同时回答“当初要求什么”和“最终选了什么” |
| 多值并存 | 无排他规则时保留并列声明 | 不按“最新一句获胜”删掉合理答案 |
| 证据矛盾且来源不明 | 保留双方归属，标记冲突 | 返回冲突或报告未知 |

**词表：稳定核心加局部扩展。** 核心只定义 Person、Entity、Event、Request、Offer、Confirmation、Claim、Evidence、Time 等基础概念，开发期冻结后全局共享。别名表把“arrive by”“no later than”映射到同一约束谓词。候选谓词找不到映射或持续出现类型冲突时，词表维护角色才提议别名、新谓词或拆分；提议由程序校验后提交，新谓词先在当前历史内临时使用。版本改变时保留旧定义，受影响的查询重新编译，所有调用照常计费。只有作用域相同且确有排他条件，才能自动写入取代事件。

**词表变更与实体合并对视图的影响。** 实体对齐发现两个实体相同时，追加一条带版本的等同条目，不改写已有声明；查询在等价类的代表元上求值。词表版本改变（别名、新谓词、谓词拆分）和实体合并都会改变声明模式的匹配关系，超出 3.4 节命题的假设。主配置取最简单的处理：事件发生时，该历史的全部常驻视图失效，下次读取时重建。事件次数和由此产生的重建 token 单独报告；若它们占维护成本的大头，再考虑只让涉及相关谓词或实体的视图失效。

### 5.3 查询编译与证据

**中间表示与编译。** 查询规划只生成有限语法的中间表示，例如 `SELECT site WHERE deployment(service=Atlas, env=prod) AT(valid=d, known=r)`。确定性编译器把它变成参数化的 SPARQL 基本图模式、受限聚合和版本过滤。语法覆盖 3.3 节的六类操作。规则模板能覆盖的任务不调用 LLM；解析或类型检查失败时退回文本检索。

下面的查询模板查“已接受的班次及其抵达时间”。它用 RDF 1.1 标准具体化书写，`ex:` 是示意用的本地前缀，`ex:knownFrom` 与 `ex:supersededAt` 代表映射到版本号的生成与失效时间。`%r%` 是截止版本的占位符：编译器在解析之前把它替换成当前读取版本的整数字面量。它不是 SPARQL 变量（`$r` 与 `?r` 在 SPARQL 中同为变量，未绑定时过滤会丢掉全部结果），也不是写死的常量，这一点决定了视图是否会过期（见 3.3 节）。

```sparql
PREFIX ex:   <https://example.org/dialogue/>
PREFIX rdf:  <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
PREFIX prov: <http://www.w3.org/ns/prov#>
SELECT ?train ?arrives ?c ?att ?a WHERE {
  ?c   rdf:subject ex:request1 ; rdf:predicate ex:selectedService ;
       rdf:object ?train ; ex:knownFrom ?r1 .
  ?att ex:about ?c ; ex:function ex:Accept ;
       prov:wasAttributedTo ex:user ; ex:knownFrom ?r2 .
  ?a   rdf:subject ?train ; rdf:predicate ex:scheduledArrival ;
       rdf:object ?arrives ; ex:knownFrom ?r3 .
  FILTER(?r1 <= %r% && ?r2 <= %r% && ?r3 <= %r%)
  FILTER NOT EXISTS { ?c ex:supersededAt ?s1 . FILTER(?s1 <= %r%) }
  FILTER NOT EXISTS { ?a ex:supersededAt ?s2 . FILTER(?s2 <= %r%) }
}
```

这个模板含两个声明模式：`(request1, selectedService, ?train)[user, accept]` 与 `(?train, scheduledArrival, ?arrives)`。它们就是该视图的依赖模式。“选中的班次”这条声明由系统在提议时引入，带（系统，提议）归属；用户接受时，在同一条声明上新增（用户，接受）归属。角色因此出现在归属上，不折进谓词。

**证据由编译器分两步取。** 主查询投影每个答案所用的声明与归属节点（上例中的 `?c`、`?att`、`?a`），它们构成见证。编译器再生成第二条查询，按这些节点取证据链接（`prov:wasDerivedFrom`）。证据不在主查询里连接，因为一条声明有多条证据时，结果行会按证据的组合成倍增加。上例的一个答案同时依赖两条消息：用户的确认和系统的提议。SPARQL 本身不返回来源，所以每个答案的证据集由编译器构造。

**范围说明。** 计数附“在截至版本 $r$ 的观察范围内计得”，空结果始终注明证据范围。范围说明由程序在读取时按当前版本生成，不属于视图内容（3.4 节）。只有来源覆盖足够时才支持穷尽性表述。

论文需要写明中间表示对应的 SPARQL 片段、它不能表达什么，以及各基准的问题落在片段之外的比例。这个比例先在阶段 1 由人工在开发历史上估计（6.5 节）。

### 5.4 视图与新鲜度维护

**两种视图。** 视图是 3.4 节定义的对象，按生命周期分两种。

- **常驻视图**在摄取期按模板清单物化，随历史持久化，在之后的读取中复用。过期判定与维护只针对常驻视图。
- **临时视图**在答题期为当前题目创建，题末丢弃，不跨题复用。这保证各题独立作答（6.8 节）。

**内容由查询给出。** 视图的答案、见证与证据由确定性查询求值得到。把结果行写成文字有两种方式，评测两种都跑（消融 C）。

- **模板序列化。** 每个查询模板配一条固定句式，程序把结果行填进去，得到事实卡。不调用 LLM。
- **LLM 渲染。** LLM 把结果行写成连贯的文字，不负责推导内容。重建的正确性因此不受写入器推导能力的限制。

模板序列化不花 LLM token，所以它不需要缓存：每次读取重新执行查询、重新填模板即可，写入侧没有渲染成本，也就谈不上过期。只有当 LLM 渲染明显更利于 reader 时，缓存渲染结果并维护其新鲜度才有意义。这是 RQ3 的前提，在阶段 2 和阶段 3 先行检验（第 9 节）。

**逐行绑定与渲染校验。** 两种方式的输出都按结果行组织：每一句标注它所表述的结果行 ID，聚合句标注聚合值及其成员行。摘要句若混杂多个事实，逐项绑定；无法绑定到结果行的句子只作为召回线索。程序据此做三件事：

- **校验 LLM 渲染。** 结果行里的每个值（实体名、数字、时间）必须在对应的句子中出现，按规范化后的字符串核对；句子中不得出现该行之外的实体名或数字。校验不过的句子换成该行的模板序列化，并计入渲染失败率。
- **局部重建。** 答案过期时，只重新生成新增或改变的行所对应的句子，删除已消失的行所对应的句子，其余句子原样保留。聚合值改变时重新生成聚合句。
- **补引用。** 引用过期时按行 ID 更新该句的证据列表，不调用 LLM。

**依赖模式的提取。** 编译器从中间表示直接给出视图的全部声明模式，包括否定条件与聚合内部的模式、各模式的归属约束，以及每个模式上只涉及该模式自身变量的局部过滤。

**过期判定的八种策略。** 系统把判定做成可替换的模块，评测比较全部八种：

| 策略 | 做法 | 预期的弱点 | 文献中的对应 |
| --- | --- | --- | --- |
| 从不失效 | 视图建成后一直复用 | 任何更新后都可能答错 | 沿用旧摘要 |
| 每轮全重建 | 每条新消息后重建所有视图 | 正确但最贵；作为等价性参照 | 每次重写摘要 |
| 仅已用声明 | 所用声明被取代时失效 | 漏掉新增匹配、命中否定条件的非取代写入、聚合成员变化 | 引用键；沿已消费记录的级联失效 |
| 已用声明加否定与聚合模式 | 在上一种之外，否定与聚合部分的声明模式有匹配写入时也失效 | 漏掉非聚合视图的新增匹配 | 引用式依赖的最强形式；为公平比较而设 |
| 谓词级 | 相关谓词有任何写入即失效 | 过度标脏，重建过多 | 粗粒度的来源键；按索引更新时间的缓存校验 |
| 声明模式依赖（推送） | 写入时把变更集与各视图的依赖模式匹配，可选加局部过滤；被标脏的视图在下次读取时重建 | 连接与否定条件下过度近似，多出不必要的重建 | 按查询模式匹配的缓存失效规则；可能与 MemShift 的定义作用域键同粒度（阶段 0 核对） |
| 读时重查加指纹（拉取） | 读取时重新执行查询；答案指纹变了才重新生成，见证或证据指纹变了只补引用 | 每次读取对每个相关视图付一次数据库查询 | 查询时现算；检索层面的读时复核 |
| 推送过滤加读时确认（混合） | 写入时按依赖模式标脏；读取时只对脏视图重查指纹，确认后才重建 | 写入侧多一次模式匹配 | 推送与拉取的组合 |

后三种都等到下次读取时才重建，它们的差别如下。

- 拉取与混合都以指纹确认为准，花费的 LLM token 严格相同。两者只差数据库开销：拉取对每个相关视图重查，混合只对脏视图重查，另付写入时的模式匹配。
- 纯推送不做确认，过度标脏的视图也会重新生成。它的 LLM token 不少于前两者，差值就是过度标脏的代价。
- 对话规模的图只有几千到几万条声明，重查是毫秒级。所以在本计划的基准上，预期拉取已经足够；推送过滤只在常驻视图多、写入频繁、图大的时候才有意义。评测用一个规模实验找这个交叉点（常驻视图数 × 写入速率 × 图规模，消融 A），不把“推送优于拉取”当作假设。

读时重查相对声明图是精确的，作为参照，其他各策略的漏报与过度标脏都对照它计数。它只相对声明图精确：抽取出错时，图上的所有策略会一起漏掉。这一部分用相对事件日志的端到端过期单独计（6.4 节）。判定模块报错或超时时，引擎回退到原文检索。

**视图选择。** 题目在摄取期不可见，所以常驻视图只能按模板清单物化。主配置使用下面六个模板族：

| 模板族 | 绑定 | 例子 |
| --- | --- | --- |
| 实体的多值属性清单 | （实体，谓词） | Melanie 会的乐器 |
| 实体的当前单值状态 | （实体，带排他规则的谓词） | 服务当前部署的站点 |
| 成员计数 | （实体，谓词） | 已提到的乐器数 |
| 任务的原始约束 | 任务 | 最初的到达要求 |
| 待确认的候选 | 任务 | 提议过但尚未被接受的班次 |
| 当前选择 | 任务 | 已接受的班次及其抵达时间 |

某个绑定下匹配的声明数达到阈值时，系统为它实例化一个视图；阈值在开发集冻结。模板清单与阈值随论文发布。按观测到的读取频率动态选择视图作为对照。

评测报告**视图命中率**：常驻视图提供了至少一项被采用证据的读取所占的比例，以及完全由常驻视图服务的读取所占的比例。命中率低说明自然数据上没有多少视图可维护，此时关于维护的结论只依据受控序列（第 9 节阶段 3 的检查点）。

### 5.5 检索、融合与组装

**检索路由。** 引擎先用结构信号选通道：编号优先 BM25，改写优先稠密，关系连接、定时、计数、纠正优先图；置信不足时用全部通道。路由规则、权重和阈值只在开发集调，并与“始终三路”对比。

**融合。** BM25、稠密、图路径的候选映射到统一的证据 ID，主配置用 RRF 排序，并与加权融合对比。

**按证据需求组装。** 引擎先保留当前任务与必要指令，为输出预留窗口，再按 token 选择记忆片段：

1. 为本次回答列出必填变量，例如“截止时间、已接受班次、班次的到达时间”。
2. 对融合后的候选，先按知晓版本、有效时间、作用域和角色过滤，再检查每个候选能支持哪些变量。
3. 在预算内按“新增需求覆盖量除以新增 token”贪心选择。同一原句可覆盖多项；一条两跳路径的两端须一起入选。
4. 仍有变量未覆盖时，展开一条摘要为原文，或追加一次受限图查询。预算耗尽时保留“未知”或部分答案，计入失败或拒答。
5. 序列化为固定布局：任务、近期原文、已核验状态、证据片段、未决项、输出契约。每个片段带稳定引用。

同一组事实可以呈现为原文、来源片段、结构化事实卡或局部状态摘要。问“班次和抵达时刻”与问“是谁确认的”时，引擎应返回不同的工作上下文。

### 5.6 下游 LLM 与角色分工

下游 LLM 只看工作上下文，不直接访问图或日志；这让同一个 reader 可以原样套在所有基线上，比较的就是上下文本身。

Reader 有四种合法输出：回答、输出状态、请求再检索一次、报告未知。离线评测中报告未知计为缺失或拒答，补问和虚构的工具结果不算成功。每次最终回答都记录所用的全部证据 ID。

系统里的 LLM 调用按角色切换模板，默认由同一个模型承担：

| 角色 | 所在层 | 何时调用 | 输入与授权输出 |
| --- | --- | --- | --- |
| 写入与实体对齐 | 图记忆 | 每条或每段需要抽取的消息（抽取粒度见消融 G）；结构化工具事件走确定性映射 | 当前消息、局部上下文、候选实体与谓词，输出带片段锚点的声明补丁 |
| 词表维护 | 图记忆 | 候选谓词无合适映射、持续类型冲突、或谓词混用导致校验失败 | 候选定义、正反例、旧版本，输出别名、新谓词或拆分的提议；由程序校验后提交 |
| 查询规划 | 上下文引擎 | 规则模板无法覆盖当前任务 | 问句、相关词表片段、时间与来源要求，输出类型化中间表示、待填变量和备选通道 |
| 核验与视图渲染 | 上下文引擎 | 程序校验遇到歧义，或需要把查询结果渲染成视图 | 查询结果、原句、预算，输出支持、冲突或未知的判定与逐句带证据的文本 |
| Reader | 下游 LLM | 每次读取 | 工作上下文与输出契约，输出回答或状态 |

**提示的组装方式。** 角色指令、输出 JSON schema 和示例在主配置中固定。调用时按需拼接的只有：当前词表版本、与当前实体和谓词有关的定义、剩余预算。固定的前缀使重试幂等，并保持前缀缓存命中。在同一历史内复用失败反例（例如某次把“最迟到达”误写成“实际抵达”）会让写入结果依赖顺序，并改变提示前缀，所以它不进主配置，只作为一个可关闭的开关在消融 F 中单独检验。

**约束。** 测试期只允许来自当前历史前缀的程序校验和原文支持，不允许用评测器或答案纠正提示。每条消息至多一次词表提议，每次读取至多一次编译修复和一次补充检索；具体上限在开发集冻结。所有调用、重试和重读都计费。

## 6. 评测协议

所有基准共用同一套系统。每条历史独立建库，各基准沿用原生的作答目标，分别报告结果。题目在指定版本的快照上独立作答，作答从不写入历史。

### 6.1 读取协议

读取点相对写入的位置，决定了一个基准能检验什么。评测使用三种读取协议。

| 协议 | 读取点 | 相邻两次读取之间的写入 | 能检验什么 |
| --- | --- | --- | --- |
| 只在末尾读 | 全部题目都在最终版本 $N$ 上 | 无 | 答案质量与证据召回；写入成本在 $M$ 次读取上的摊薄；常驻视图的命中率；对摄取期物化的常驻视图，过期判定的召回 |
| 逐轮读 | 每个用户轮之后 | 一到两条消息 | 角色处理与增量状态；短历史上的过度标脏 |
| 交替读写 | 散布在历史各处的版本 | 视协议而定 | 长历史上过期判定的精确率与召回率，以及维护成本 |

由第 3 节可以推出两点。

- **只在末尾读时，判定粒度改变不了成本。** 最便宜的正确策略是在版本 $N$ 统一把每个视图建一次。摄取期物化的视图到 $N$ 时很可能已经过期，所以漏判的策略在这里照样会答错；但在读取之前，每种策略对每个视图至多渲染一次，更细的判定省不下重建。$N$ 上的 $M$ 道题之间没有写入，所以常驻视图在版本 $N$ 重建一次之后，对这 $M$ 道题一直新鲜。答题期的临时视图题末丢弃，不跨题复用，跨题复用只来自常驻视图。这 $M$ 次读取测的是常驻视图的复用与写入摊薄，不是维护。
- **关于维护成本的主张只在交替读写下检验。** 对应的是受控变更序列和 LoCoMo 的按证据锚定流式问答（6.5 节）。MultiWOZ 的对话只有十几轮，逐轮读取给出过度标脏的自然数据，但不支撑任何成本结论。

### 6.2 基准与术语对应

各数据集对同一层结构的叫法不同，本计划统一把记忆的单位称为**历史**。LoCoMo 的 conversation 指整条独立历史，大致相当于一些 agent 基准与文章所说的一个完整 session；而 LoCoMo 与 LongMemEval 又把历史内部带日期的分段叫作 session。对应关系只在此处给出。

| 基准 | 一条历史（记忆单位） | 历史内的分段 | 单条消息 |
| --- | --- | --- | --- |
| 受控变更序列 | 一条生成的序列 | episode（由生成器定义） | 消息 |
| MultiWOZ | dialogue（`dialogue_id`） | 无 | turn |
| LoCoMo | conversation（`sample_id`） | session（带日期） | turn（`dia_id`） |
| LongMemEval | 每个 `question_id` 自带的 chat history | session（带时间戳的一次独立对话） | turn |
| HaluMem | 每位用户的全部会话 | session | turn |
| MemoryAgentBench | 一个 context | chunk（逐块喂入） | 无统一单位 |

### 6.3 基准、分档与读取协议

基准分三档。档位决定结果在论文中的位置和执行的先后。标“核心”的属于 9.3 节的最小可发表核心，标“可选”的在有余力时再做。

| 基准 | 档位 | 读取协议 | 主指标 | 服务的问题 |
| --- | --- | --- | --- | --- |
| 受控变更序列（自建） | 正文（核心） | 交替读写；读取点由生成器安排，每条消息后都可读 | 过期判定相对读时重查的精确率与召回率；相对事件日志的端到端过期召回；与全重建的答案一致率；重建 token | RQ2（主证据）、RQ3 维护成本面 |
| MultiWOZ 2.4（主）；2.2 与 2.1 对同一份预测另行计分 | 正文（核心），定位为专项诊断 | 逐轮读：每条 dialogue 独立初始化，按真实消息增量写入；每个用户轮只看当时前缀，预测累计状态 | 提议之后各轮的原始约束保持率；“原始约束”与“当前选择”的成对正确率；旧值误用率；整体 JGA 与 slot F1 作参照 | RQ1（角色的主证据）；自然逐轮数据上的过度标脏 |
| LoCoMo | 正文（核心） | 只在末尾读（原生），另加按证据锚定的流式问答 | token-F1 与校准过的盲评准确率；证据召回；视图命中率；流式下 $v(q)$ 与 $N$ 两次作答的一致率、过度标脏率与重建 token；累计 token 对读取次数的曲线；七类变更的自然分布（开发历史） | RQ1、RQ2（自然分布与误报）、RQ3 摊薄 |
| LongMemEval-S（清洗版） | 正文，不利设定；取三个分层 | 只在末尾读，每条历史一问；摄取全部 session，保留 `question_date`，屏蔽 `has_answer` 与 `answer_session_ids` | 官方 GPT-4o 分题型判分的准确率；段级与轮级证据召回 | RQ1、RQ3 的不利设定 |
| HaluMem-Medium | 汇总表（可选） | 逐段摄取；按金标记忆点和更新标记为抽取与更新打分 | 抽取与更新的操作级正确率；问答准确率 | 图质量；RQ2 佐证 |
| MemoryAgentBench：LongMemEval(S\*) 与 FactConsolidation 的 6K、32K 变体 | 汇总表（可选） | 上下文逐块喂入，之后对同一上下文回答多道题 | 各能力维度的准确率；累计 token 对读取次数的曲线 | RQ3 多次读取设定；FactConsolidation 作 RQ2 佐证 |

考虑过但不评测的基准：BEAM、Memora、STALE。BEAM 覆盖知识更新与矛盾消解，可佐证 RQ1 与 RQ2；Memora 与 STALE 只能佐证 RQ2。三者都没有逐消息的视图失效真值，每加一个都要多一份适配器、判分器和各自的许可约束。它们保留在相关工作中。阶段 6 之后若仍有预算，可以把其中一个放进补充材料，并标明是锁定之后补做的；首选 BEAM 的 128K 档。STALE 的数据能否下载尚未确认，使用前先核实。

### 6.4 受控变更序列

受控序列是 RQ2 的主证据，所以它的设计在看到任何过期判定结果之前就固定。针对含显式双时间问题的对话记忆基准做过检索，没有找到；这是基于有限检索的弱否定证据。已有的受控修订生成器（StateMemBench 等）要引用并区分：它们没有双时间成对问题，也没有逐消息的视图失效真值。

**内容。** 以程序事件日志为真值的自然英文对话。覆盖七类变更：取代被引用的声明；新增匹配（含空变非空）；否定命中，即一次接受或拒绝使答案消失或出现，而不取代任何声明；计数或排序变化；迟到更正；重复提及，它只引起引用过期；无关更新。另含提出但始终未确认的备选、预设了过期状态的问题，以及成对的“当时所知”与“现在回看”问题。

**每条序列的生成器输出。** 消息序列；事件日志；每个版本上的金标声明图（含归属与证据链接）；带金标答案与见证集的读取安排；以及每个模板视图在每条消息之后是否答案过期、是否引用过期（逐消息的失效真值）。

**受控变量。** 变更类型的配比；修订密度（每 100 条消息中的变更数）；读取间隔（相邻两次读取之间的消息数）；每条历史的读取次数；历史长度。RQ3 的维护成本面，是在固定长度下让修订密度与每条历史的读取次数交叉变化测得的。

**两个参照。** 过期判定在两个参照下评测，漏报按来源分开计。

- 相对声明图的参照是读时重查。它衡量判定策略本身：在同一张图上，某个策略漏掉了多少、多标了多少。
- 相对事件日志的参照是逐消息的失效真值。它衡量端到端：真值说视图已过期，而系统仍把旧内容交给 reader 的比例。
- 在抽取图上，端到端漏报减去判定漏报，就是抽取导致的漏报（例如单簧管被抽成了另一个谓词，图上的所有策略包括读时重查都会漏）。

在金标图上，声明模式级不漏报是定理，引用式策略的漏报率由配置的变更配比决定。金标图实验因此是实现的正确性检查和过度标脏的测量，不当作经验发现。经验问题是各类变更在自然对话中出现的频率，由 6.5 节的自然分布测量回答。

**有效性。**

- 表层文字由一个不被任何受评系统使用的模型渲染，使任何系统都不与生成器共享措辞。
- 两名标注者对照事件日志抽审序列的语义：每个模板族至少抽 5 条序列，逐消息判断文字与事件是否一致，报告 Cohen's κ 与分歧率。标注者是一名作者和一名不参与系统开发的人，人选在阶段 1 确定。
- 按模板族切分：开发与留出的模板族互不相交。
- 合成数据上的高分不替代自然基准上的结果，论文中明确写出。

完整设计（事件语法、模板、渲染、抽审流程、规模）是阶段 1 产出的单独文档（任务 T008）。生成器的实现是阶段 2 的第一项工作。

### 6.5 各基准的要点

**MultiWOZ。**

- 测试集 1,000 条 dialogue、7,372 个用户轮。
- 预测器把内部图投影到官方槽位，这一投影同样提供给所有具有结构化内部状态的系统。
- 2.4 是对同一批测试对话的重标注，所以同一份预测对 2.4、2.2、2.1 分别计分不增加推理开销。2.1 一行用于与零样本 LLM 的已发表结果对照。
- 不读取后续轮次，不回填金标状态。
- 两件事在阶段 1 从数据上确定（任务 T006）后才写进论文：“2.2 把系统提议的值写入状态、2.4 不写”是否普遍成立；测试集中接受或拒绝系统提议的轮次有多少。
- **指标的操作化。** “当前选择”（如车次号）不是官方槽位，所以分两个指标。原始约束保持率只用 2.4 的官方金标：在系统提议之后的各轮，预测状态是否保留用户约束的原值。成对正确率需要派生金标：按系统轮的对话行为标注取出被提议的实体，按下一用户轮的行为判定接受或拒绝，由规则生成“当前选择”；一道题要同时答对“原始约束”和“当前选择”才算对。派生规则由两名标注者在 200 个轮次上核验，报告 Cohen's κ，规则与核验结果在 T006 中确定并发布。
- **只赢在标注惯例上不算数。** 一条“系统值不写入”的确定性规则在原始约束保持率上应当与角色守卫打平，TripPy 的 system-inform memory 也早已这样做。这只说明规则与 2.4 的惯例一致。角色守卫的证据是成对正确率：那条规则答不出“当前选择”，把系统值直接写入的做法答不对“原始约束”。
- 提议轮次数决定 MultiWOZ 在 RQ1 中的分量。准确率在 70% 左右时，约 400 个轮次给出约 4.5 个点的 95% 区间半宽。若实际轮次数对应的半宽超过 5 个点，角色主张的主证据改为受控序列，MultiWOZ 退为佐证。
- MultiWOZ 的对话很短，全历史始终放得进窗口。计划不在它上面做任何成本或维护的论证。

**LoCoMo。**

- 公开文件含 10 条历史、1,986 题。按官方评测代码，类别 1 是 multi-hop（282 题）、2 是 temporal（321）、3 是 open-domain（96）、4 是 single-hop（841）、5 是 adversarial（446）。
- 主评测用类别 1 到 4 共 1,540 题。conv-26 与 conv-49 作开发集（308 题），其余 8 条留出（1,232 题）。
- 类别 5 若评测拒答则单列，并说明判分方式。
- 输入统一排除图片、图片描述与人工摘要；答案只出现在图片描述里的题目单列。
- LoCoMo 没有以更新为中心的问题；只在末尾读时它对 RQ2 没有贡献，论文中直接说明。
- **片段覆盖率。** 阶段 1 由人工标注两条开发历史的 308 题：每题能否用 3.3 节的片段表达，不能时属于哪一类（开放推理、日期运算、常识、其他）。两名标注者在其中 100 题上重叠，报告 Cohen's κ。覆盖率是图通道准确率的上限，它低于一半时 RQ1 在 LoCoMo 上的预期随之下调（第 9 节）。
- 一份独立审计称 1,540 题中 99 题答案有误，另有 57 题证据标注有误。审计者为匿名账号，与一个竞争性记忆产品有关联，未经同行评审，但逐题清单公开。计划抽查该清单，并同时报告全部 1,540 题和剔除 99 题后的 1,441 题。

**LoCoMo 的按证据锚定流式问答。** 每道题 $q$ 在版本 $v(q)$ 提问一次，即其标注证据中最晚一轮所在 session 的结束处，到 $N$ 时再问一次。每次读取后继续写入；该题的临时产物照常丢弃。

- 金标不用重新标注即仍然有效：金标是在整条历史上标的，而到 $v(q)$ 时全部标注证据都已出现。这一点在证据标注完整的范围内成立。证据缺失或无法解析的 13 题不参加流式问答，审计证据错误清单上的题目单列。
- 读取与写入因此交替进行：摄取期持久化的视图在散布的版本上被读取，又被之后的写入弄过期，各过期判定策略的成本差异就在自然数据上体现出来。
- 同一道题在 $v(q)$ 与 $N$ 各问一次、对照同一个金标，构成一致性检验：答案变了，说明之后的写入干扰了系统（错误取代，或误判过期后重建得更差）。
- 局限：题目只在证据完整之后才提问，所以测不到“答案本应改变”的真过期，例如在提到小提琴和提到单簧管之间问乐器。这个协议测的是误报的代价与复用的收益；漏报与真过期由受控序列测量。
- 它是否进正文，取决于 $v(q)$ 分布得有多散（任务 T007）。若相当比例的留出题 $v(q)$ 落在最后一个 session 之前，且相邻读取之间确有写入，就在正文报告；否则移入补充材料。具体阈值在使用留出数据之前，由开发历史确定。

**自然过期分布的测量。** 这项测量回答“引用式依赖漏掉的变化在自然对话里有多常见”，不花 reader token。

- 数据是 LoCoMo 两条开发历史和 LongMemEval 开发历史的抽取图。LoCoMo 的两条开发历史由人工校正抽取结果。
- 对 5.4 节的每个模板视图，逐消息重新执行查询，把每次变化归入七类变更之一，并区分答案过期与引用过期。
- 报告各类变更每千条消息出现的次数、引用过期与答案过期之比，以及引用式的两种策略在这些自然变化上各漏掉多少。
- 阶段 1 先用一次性的抽取提示和手写查询做粗测，阶段 3 用正式的写入器和编译器重做。

**LongMemEval-S。**

- 500 题，每题自带约 11.5 万 token 的历史；其中知识更新题 78 道、时间推理题 133 道（分题型计数取自后续论文的表格，下载后从文件复算）。
- 正文用三个分层：知识更新、时间推理和多会话（多会话的题数从文件复算）。全集有余力时在补充材料中报告。
- 知识更新分层与本计划的主张最相关，但只有 78 题，留出约 62 题；准确率在 70% 时 95% 区间的半宽约 11 个点。这个分层只作描述性报告，不做显著性结论。
- 按题型和拒答标签分层切分，约 20% 开发、80% 留出，发布实际清单。
- 每条历史只有一问，是摊销写入成本最不利的设定，计划如实报告。
- 历史超出主模型的原生窗口，全历史基线由长上下文的第二 reader 承担。它是算力开销最大的一项：算力预算最先为它预留，执行排在核心完成之后（9.3 节）。

**HaluMem-Medium。**

- 20 位用户，每位约 70 个 session、约 16 万 token；14,948 个记忆点，3,467 道题，其中 180 道动态更新题、769 道记忆冲突题。
- 它提供逐段的金标记忆点、更新标记和被替换记忆的链接，可以把写入路径与问答分开打分。它的更新任务对应“声明被修订”，不对应插入引发的视图过期。
- 数据为合成，原论文的判分与作答都用 GPT-4o。
- 许可是 CC BY-NC-ND 4.0，不能发布改注后的子集。

**MemoryAgentBench。**

- 上下文长度 10 万到 144 万 token，增量喂入且一个上下文多道题；它也让评测走出双人对话。
- 其中的 LongMemEval(S\*)（5 个上下文、300 道题）是多次读取版的 LongMemEval，对 RQ3 最有用。
- FactConsolidation 由反事实编辑对拼接而成，不含对话、说话人和归属。在 26.2 万 token 的多跳子任务上，已发表方法都不超过 7%，存在地板效应；计划只用放得进主模型窗口的 6K 与 32K 变体，结果单列。

### 6.7 指标

指标按三层分别计，使“存对了没有”“给对了没有”“答对了没有”可以分开归因。

$$
\mathrm{Acc}=\frac{1}{|I|}\sum_{i\in I}J(q_i,g_i,a_i),\qquad
\mathrm{Recall}_i=\frac{|R_i\cap e_i|}{|e_i|},\qquad
\mathrm{Full}_i=\mathbf 1[e_i\subseteq R_i]
$$

| 层 | 指标 | 说明 |
| --- | --- | --- |
| 图记忆（存储状态） | 声明的精确率、召回率与 F1；结构校验符合率与重试次数；所引片段是否蕴含该声明；角色与时间字段准确率；复述被当作独立证据的比例；答案覆盖上界 | 在抽样标注、HaluMem 金标记忆点和受控序列的金标图上计算。召回需要穷举一段消息里的全部声明，成本高，所以只在抽样的片段上做：从开发历史抽 40 段、每段约 20 条消息，两名标注者独立标注后合并，报告声明级的一致率。MultiWOZ 的对话行为标注可用于校验角色（各版本文件是否保留该标注在阶段 1 核对） |
| 上下文引擎（呈给 reader 的上下文） | 证据召回与完整命中；视图命中率；过期判定的精确率与召回率，答案过期与引用过期分开，判定漏报与抽取导致的漏报分开；视图与全量重算的一致率；过期内容进入提示的比例；渲染校验失败率；解析失败率与回退到文本检索的比例 | 检索候选与真正呈给 reader 的证据分开计 |
| 下游 LLM（最终答案） | 准确率 Acc（$J$ 为预注册的二元语义判分）；token-F1；JGA 与 slot F1；无依据作答率；旧值误用率；拒答正确率；流式下 $v(q)$ 与 $N$ 两次作答的一致率 | 各基准沿用原生指标，另报统一的盲评准确率 |

**证据召回报两个口径。** 严格口径只在原句进入提示时计命中；宽松口径把派生项按来源链接计入。一项审计显示这个选择会改变绝大多数查询的排序指标并翻转系统排名，所以两者都报，并说明每个基线的证据集如何提取。标注证据可能只列了一组可用来源，预先抽样人工核验替代来源，避免误判。

**判分器校准。** 盲评判分器固定模型快照与提示，并加入“刻意写错的含糊答案”作负对照。LoCoMo 的独立审计报告，常用的 gpt-4o-mini 判分器对这类答案的接受率是 62.81%。所有系统固定同一个回答提示，因为回答提示本身就能让同一 reader 的准确率相差十个点以上。

**分层报告。** 结果按历史的 token 长度分位、修订频率、每条历史的实际读取次数、标注证据覆盖的分段数分层，并明确报告不占优的区域。分层标签只在评分端使用。

### 6.8 防泄漏与验证

写入期不可见题目、参考答案与证据标注。其余规则：

- 所有基线共享相同的日期与可见信息；凡人为缩短输入历史的实验，结果表中标明可见范围和选取依据。
- 答题期的临时视图、编译修复和生成的回答在题末丢弃，不追加到历史。流式问答下每个读取点都遵守这一条。
- 用固定解码抽样对比两种题序，检查索引版本和每题输入证据是否一致。
- 完美抽取图、完美中间表示和金标证据只出现在明确标记的误差上界实验里。
- 在人工标注子集上核查中间表示的角色、时间过滤、原文引用和执行结果。
- 冻结并发布切分、排除原因及各类数量。

### 6.9 统计分析

主分析用题目级配对检验加以历史为随机效应的模型，逐簇差值和留一簇作敏感性分析。

- **LoCoMo 只有 8 个留出簇。** 双侧符号检验需要 8 条历史全部同向才达到 p ≈ 0.008，7 条同向时 p ≈ 0.07。即使把 1,232 题当作独立样本，准确率在 80% 到 90% 时 95% 区间的半宽也有约 1.7 到 2.2 个点。所以不在 LoCoMo 上宣称 1 个百分点的非劣效。
- **质量对齐的判据。** 非劣效界限在开发期按各基准的样本量预注册；数据不足以支撑时只报配对差的置信区间，不宣称等效。统计功效主要来自受控序列、MultiWOZ、LongMemEval 与 HaluMem。
- **预注册的形式。** 协议文件（切分、指标、非劣效界限、判分提示、主配置）在跑任何留出数据之前提交到仓库并打标签，文件的 SHA-256 与提交哈希写进论文；同一份文件在 OSF 登记，以取得第三方时间戳。
- **小子集只作描述。** LoCoMo 的 open-domain 只有 96 题；LongMemEval 的知识更新分层留出约 62 题；单段偏好题和拒答题各 30 题，切分后留出约 24 题。
- **不确定性分来源报告。** 判分器重复运行、回答提示、reader、抽样误差和标签噪声分别给出，不只报第一项。
- **聚类单位。** 受控序列按模板族，LoCoMo 按 conversation，LongMemEval 按评测实例并检查高度重合的历史，MultiWOZ 按 dialogue，HaluMem 按用户，MemoryAgentBench 按 context。

## 7. 模型、基线与消融

所有对比固定同一个 reader、同一个回答提示和同一组上下文预算，变化的只有“交给 reader 的上下文是怎么来的”。

### 7.1 模型配置

| 配置项 | 选择 | 理由与注意事项 |
| --- | --- | --- |
| 主模型 | Qwen3-8B，承担写入、规划、渲染和 reader；关闭 thinking，冻结 chat template 与 tokenizer | 与 ProgMem、ReacTOD 的骨干一致，便于对照。原生上下文 32,768 token。关闭 thinking 可能压低写入器的抽取质量，所以“写入器打开 thinking”是消融 G 的一个水平 |
| 解码 | 温度 0 | 模型卡对非 thinking 模式建议 T=0.7；取 0 是为可复现做的有意偏离，另报建议设置下的敏感性 |
| 当代小模型 | 一个与主模型同量级、发布晚于 Qwen3 的开放权重模型，在阶段 1 选定 | Qwen3 发布于 2025 年 4 月，其后已有数代开放权重模型。及早选定，可以让提示同时为两个模型冻结；主要结论在阶段 7 于其上重复 |
| 长上下文第二 reader | 一个原生窗口能装下 LongMemEval-S 全历史的开放权重模型，在阶段 1 对照模型卡核对许可与上下文长度后选定 | 承担长历史上的全历史基线，并复核模型规模的影响 |
| 写入器规模 | 在预注册的分层子集上，用主模型同系列的大模型同时替换写入器与 reader | 估计写入瓶颈；只声称同系列内的规模效应 |
| 嵌入 | Qwen3-Embedding-0.6B；冻结并公布查询指令字符串 | BM25 使用相同分词与分块；较短的历史精确算余弦，不用近似索引 |
| 重排 | 主配置不加交叉编码器 | 避免把重排增益误归因于图；重排作为单独一组对照，对所有方法同时打开 |
| 判分 | 盲评判分器固定模型快照，在阶段 1 按“到论文发表时仍可用”选定；LongMemEval 在可用时另用其官方判分器 | 在开发集上测量固定判分器与官方判分器的一致率并报告 |
| 算力 | 本地 8×B200 并行处理多条独立历史；外部 API 只用于独立盲评与分歧复核 | API 不参与任何图更新决策 |

### 7.2 基线

下列基线都在本计划的协议下运行，使用相同的 reader 与预算。

| 类别 | 基线 | 要排除的解释 |
| --- | --- | --- |
| 原文 | 全历史，分有无前缀缓存；last-k；截断到同一预算 | 较短的完整原文可能已经最优。全文超出窗口时披露比例，不静默截断 |
| 检索 | BM25、稠密、两者的 RRF 融合 | 仅靠强文本召回就能解释收益。这是 RQ1 的直接对照 |
| 检索 | 上一行的 RRF 融合，每个文本块前加说话人与对话行为标签（标签由同一个写入器预测，其 token 计入成本） | 最便宜的角色方案。它若拿到大部分角色收益，结论收窄为“角色信息有用” |
| 压缩 | 滚动摘要加近期原文：每次更新后重写，以及不重写、沿用旧摘要 | 压缩本身就够；两种做法分别对应“贵”与“会错” |
| 结构化 | 固定 schema 的槽位表，带角色与来源；槽位在开发集上定义后冻结 | 结构化字段本身就够，不需要开放谓词。字段相同的关系编码与图是同一数据模型，计划不比较两种引擎 |
| 结构化 | 本系统的模板序列化变体：每次读取重跑查询，结果填进固定句式，不渲染、不缓存 | LLM 渲染与缓存是否必要。它若在 reader 准确率上打平，视图维护就没有成本上的意义 |
| 结构化 | 同骨干的“只追加、查询时解决冲突、不缓存”记忆 | 持久化视图是否必要。这是成本问题上最直接的对手 |
| 外部系统 | Mem0（属于最小核心）与 Mem0g（可选） | 近年对比表中最常见的参照 |
| 外部系统 | Graphiti（可选），公布适配方式与失败率，另列其原生骨干一行 | 一个带失效机制的时序图记忆。小模型下的表现在文献中互相矛盾：Zep 的 LoCoMo token-F1 在一项复现中是 33.82（Qwen2.5-7B），在 ProgMem 的表中是 13.82（Qwen3-8B） |
| MultiWOZ | 在 Qwen3-8B 上复现 ReacTOD；基于官方槽位的确定性覆盖更新；“系统值不写入”的确定性规则；同 reader 直接输出累计状态 | ReacTOD 用 Qwen3-8B 零样本在 MultiWOZ 2.1 上报 47.34 JGA（带校验循环），且只报告 2.1。“系统值不写入”的规则用来分开“与标注惯例一致”和“角色守卫有用” |

八种过期判定策略在消融 A 中比较，全部在同一声明图上实现，并在 5.4 节逐一对应到已发表的依赖键与缓存失效规则。固定 schema 的时序图是消融 F 中的一臂。

**仅作参考、不在本协议下复跑。** 引用分数时注明骨干与指标，不当作同协议结果。

| 工作 | 不复跑的理由 |
| --- | --- |
| APEX-MEM、ProgMem | 协议不同；查询时解决的基线与 Qwen3-8B 骨干已覆盖这一比较 |
| MemShift、Tether | 它们的依赖键在消融 A 中作为策略重新实现；代码条件允许时，在同骨干下复跑其依赖键作核对 |
| LightMem、层级式系统（如 MemOS） | 增加广度，但不对应一个需要排除的独立解释 |
| 原文搜索 agent（grep、search、open） | 开销大，而主要比较针对的是上下文如何构造；Letta 报告这类 agent 用 gpt-4o-mini 在 LoCoMo 上得 74.0%（LLM 判分，厂商报告）。可以在开发集上运行，放进补充材料 |
| 按 LongMemEval 配方调优的 RAG（按轮存储、事实并入索引键、时间感知的查询扩展、Chain-of-Note 阅读） | 其 reader 侧技巧与“固定回答提示”冲突，且与上下文如何构造正交 |

### 7.3 消融

## 8. 成本口径

主结果用缓存调整后的口径，并且只在质量对齐的配对上解读成本差异。

### 8.1 记账规则

- 逐调用记录输入与输出 token，覆盖抽取、校验、词表、规划、渲染、重试和作答。失败的尝试照计。
- 工具或查询结果进入下一次提示时，在该次输入中计数。
- 每个方法报三本账：逻辑 token、前缀缓存复用后实际计算的 token、GPU 秒。
- 嵌入编码 token、数据库 CPU、内存、p50 与 p95 延迟、工具调用次数单列。
- 盲评调用另列为评测开销，不计入系统成本。
- 不同模型的同数 token 不解释为相同价格。
- 所有方法使用对缓存友好的同一提示布局：稳定内容在前，随题目变化的内容在后。
- Reader 的记忆片段预算取 256、512、1,024 token 和实际全历史四档；系统指令、当前问句和输出预留固定，另公布真实总输入。

### 8.2 公式

固定一条历史、$M$ 道独立题目。全历史基线在无缓存与有缓存两种口径下的开销，以及本系统的开销：

$$
T_{\mathrm{full}}=M\,H+\sum_{i=1}^{M}\bigl[L(q_i)+L(g_i)\bigr],\qquad
T_{\mathrm{full}}^{\mathrm{cache}}=H+c\,(M-1)\,H+\sum_{i=1}^{M}\bigl[L(q_i)+L(g_i)\bigr]
$$

$$
T_{\mathrm{sys}}=W(\mathcal H)+\sum_{i=1}^{M}\bigl(U_i+A_i\bigr),\qquad
M^{*}=\left\lceil \frac{W}{\Delta}\right\rceil
$$

$H$ 是序列化历史的 token 数；$c$ 是缓存命中的输入相对全价的比例，本地推理用实测的计算量比，API 用其计费比。$W$ 是一次完整摄取中用于抽取、建图、词表和视图维护的 LLM token；$U_i$ 是第 $i$ 题的规划、核验与修复；$A_i$ 是最终回答的输入与输出。$\Delta$ 是缓存调整后全历史每题比本系统多花的 token；$\Delta$ 非正时没有回本点。逐轮读与交替读写时，把 $W$ 换成每次读取之前新增的写入成本之和，全历史基线按每次读取时的实际前缀长度计。历史只追加，前缀稳定，所以全历史基线在交替读写下同样吃前缀缓存：每次读取只对上次读取之后新增的消息付全价，其余按缓存比 $c$ 计。有缓存的全历史一行按这个口径实测，不按无缓存估计。

### 8.3 要报告的结果

- **质量对总 token 的曲线。** 相同预算比准确率；相近质量比平均 token。
- **摊薄曲线。** 在同一快照上固定种子抽取不同数量的独立题目，复用同一次写入，画累计 token 对读取次数的曲线，报告达到质量阈值时的交点。在 LoCoMo 与 MemoryAgentBench 的 LongMemEval(S\*) 上运行。对手是带前缀缓存的全历史、不缓存的查询时解决，以及本系统的模板序列化变体。这些曲线测的是写入摊薄与视图复用，不是维护（6.1 节）。
- **维护成本面。** 在受控序列上让修订密度与每条历史的读取次数交叉变化，对每种过期判定策略报告重建 token，以及相对全历史和查询时解决的总成本。LoCoMo 流式问答给出这张面上的一个自然数据点。
- **每成功任务成本。** 含失败成本的总量除以成功数，附成功率；无成功则记为未定义。
- **缓存前后对照。** 同一组结果在两种口径下各报一次。回本读取次数 $M^{*}$ 画成关于缓存比 $c$ 的曲线，$c$ 从 0 到 1 取值并标出实测值，不只报一两个点。

### 8.4 由口径推出的设计约束

下面几条是按文献数字做的粗算，不是实测，用来定写入预算的量级。

- **LoCoMo。** 每条历史约 150 题。每条历史的 token 数在不同来源中有约 8 千、9 千、1.6 万、2.6 万四种说法，须用主模型的分词器重新计数。按 2 万计，不缓存时全历史一侧共约 300 万输入 token；若缓存命中的输入按一成计，只相当于三十万左右。所以写入器在每条历史上的预算应控制在十万 token 量级，具体数字在重新计数后确定。
- **这个预算下逐消息抽取做不到。** 一条历史约 600 轮（下载后复算），十万 token 摊到每条消息不到 170 token，而一次抽取调用要装下指令、schema、候选实体、示例和输出。可行的做法只有两种：按若干条消息或按 session 分段批量抽取；或让固定的指令前缀吃前缀缓存，只对变化的部分付全价。抽取粒度因此是一个设计变量（消融 G）。阶段 1 先在纸面上核算各粒度下的写入 token，对照带缓存的全历史画出关于 $c$ 的回本曲线，做出“做或不做”的判断；LoCoMo 上回本不成立时，直接写明，成本主张只依据读取次数更多的设定。分段抽取时，声明的知晓版本仍取其证据消息的版本；读取落在一段中间时，先抽取已到达的部分再作答，这次调用照常计费。
- **LongMemEval。** 每条历史只有一题，写入成本超过约 11.5 万 token 的方法不可能在 token 上回本。这里要比的是质量和 reader 窗口占用，计划不在该基准上声称端到端省 token。
- **算力。** LongMemEval-S 的原始历史合计约 5,750 万 token。按已发表的同骨干构建成本推算，全集的写入侧在 0.8 亿到 6.8 亿 token 之间，超过其他基准之和；这正是正文只用三个分层的原因。

“计入写入”和“回本题数”已有发表先例，写入侧 token 也已常有报告。本计划的增量限定在四项：质量对齐的比较、含失败尝试的每成功任务成本、更新之下的维护成本、开放小模型上的缓存前后对照。别的论文报告的写入成本不直接引用作对比，因为同一系统在不同论文里的记账可相差一个数量级；所有基线都在同一口径下重测。

### 9.1 结论边界

- 若只减少 reader 输入却增加端到端 token，结论收窄为“提高了窗口利用率”。
- 若模板序列化的事实卡与 LLM 渲染的视图在 reader 准确率上相当，论文讲“过期判据加查询时现算”，不声称维护视图更省。
- 若加标签的混合检索拿到大部分角色收益，只声称角色信息有用。若“系统值不写入”的规则在成对正确率上也打平，不声称角色守卫的作用。
- 若固定槽位表在开放域切片上与声明图相当，不声称开放谓词的收益。任何情况下都不声称图优于字段相同的关系表。
- 若读时重查在规模实验的全部范围内同样准确且不更贵，结论写作“过期判据及其评测”，推送式匹配作为一种实现报告。
- 若双时间只在合成数据上有收益，只声称系统能处理该机制。
- 若短历史普遍是全文最优，把“何时启用图通道”作为实证结果；这一结论已有类似报告，只作为旁证。
- 关于维护成本的主张只依据交替读写；只在末尾读时的写入摊薄，绝不当作维护方面的证据。MultiWOZ 上不做成本论证。
- 金标图上的结果是正确性检查，不当作经验发现；经验结论来自抽取图和自然分布测量。
- 所有性能改善、绝对耗时和 API 费用均待实测，计划不预设数值。

## 10. 风险与应对

最大的风险有四个：声明模式级依赖可能已被近邻预印本覆盖；模板序列化可能使缓存视图失去必要性；小模型写入器的抽取质量会同时拉低图通道和依赖它的每一项结论；读时重查可能使推送式判定失去必要性。

| 风险 | 依据或表现 | 应对 |
| --- | --- | --- |
| 声明模式级依赖已被覆盖 | MemShift 的定义作用域键可能是同一粒度；其附录、Martin 等（2010）和 Tether 的后三分之二尚未读完 | 阶段 0 排在所有工作之前；读完之前相关措辞标为暂定；被覆盖时贡献收为两级过期、RDF 上的形式化和自然对话评测 |
| 模板序列化就够了 | 视图内容由确定性查询给出，LLM 只负责写成文字；事实卡可能同样好读 | 模板臂进正文，阶段 2 就跑；它打平时论文讲“过期判据加查询时现算”，过期定义、判定评测和自然分布测量仍然成立 |
| 写入器抽取不可靠 | 小模型的结构化写入格式错误率高；多数系统漏掉大量应做的更新 | 输出受 JSON schema 约束并经结构校验；失败时保留原文路径；图质量单独成表；金标图与抽取图分开报告，判定漏报与抽取导致的漏报分开计；用大写入器和打开 thinking 估计上限 |
| 写入预算回不了本 | LoCoMo 上每条消息的预算不到 170 token，逐消息抽取做不到 | 抽取粒度作为设计变量；阶段 1 先做纸面核算并画关于 $c$ 的回本曲线；回不了本时不在该基准上声称省 token |
| 读时重查就够了 | 已发表的“查询时现算”数字不差；对话规模的图上重查是毫秒级，不花 LLM token | 把读时重查列为正式实验臂和精确参照；加入混合臂和规模实验，报告推送开始划算的交叉点；论文写成即使它胜出结果仍成立 |
| 自然数据中交替读写太少 | 只在末尾读的基准测不出维护；LoCoMo 流式问答的 $v(q)$ 可能分布集中；常驻视图的命中率可能很低 | 维护主张依靠受控序列；报告视图命中率；只有 T007 显示分布足够分散时，LoCoMo 流式问答才进正文 |
| 自然对话里变更太少 | LoCoMo 没有以更新为中心的问题；流式协议按设计测不到真过期 | 在开发历史的抽取图上逐消息重查，直接测七类变更的自然分布；结果少就如实写明适用负载 |
| 合成序列不被认可 | RQ2 的主证据是生成数据；金标图上不漏报是定理，漏报率由配比决定 | 金标图结果只当作正确性检查；经验结论来自抽取图和自然分布测量；生成器设计在看到结果之前固定；由受评系统之外的模型渲染；双人抽审；按模板族切分；发布生成器与日志 |
| 空缺被抢先 | 近两个月出现至少五篇相关预印本，其中两篇把派生记忆表述为视图 | 阶段 2 结束后先发预印本（9.3 节）；定稿前重新检索，并检索数据库领域“由 LLM 维护的物化视图”方向 |
| 与语义网的相关性受质疑 | 相关性是第一条评审标准；征稿主题中没有智能体或记忆；评审会问“为什么是 RDF” | 不主张图优于关系表。回答落在四点：声明、归属、来源、时间各用标准词表（RDF 1.2 reifier、PROV-O、OWL-Time），校验用 SHACL，查询是 SPARQL 的一个明确片段，记忆可以被其他工具读取和核验；开放谓词的收益由固定槽位表的对照检验 |
| 形式化被认为不新 | 可靠性命题是已知结果的实例 | 如实标注；新意限定在两级过期、覆盖归属与证据的四类条目、对话负载上的实测 |
| 查询规划出错 | LLM 直接写 SPARQL 的系统败在实体绑定、静默空结果和缺聚合 | 只生成受限中间表示；类型检查；空结果注明证据范围；失败回退到文本检索并计入回退率 |
| 全历史基线赢 | 短历史放得进窗口，读全文往往是最强的一行 | 按历史长度和读取次数分层；明确报告不占优区域；结论写成适用条件而非普遍优势 |
| 图相对平面结构没有收益 | 小规模下平面记忆与图记忆的准确率几乎相同；多数题可能落在查询片段之外 | 阶段 1 先测片段覆盖率；角色、表示与时间做 2×2×2；只在连接、计数、按时点查询的切片上找图通道的价值 |
| 角色守卫的作用无先例支持 | 对话状态追踪之外没有研究检验提议与请求之分；在 MultiWOZ 上得分可能只是投影规则符合标注惯例 | 作为 RQ1 中带收窄条件的假设；用成对正确率，并加“系统值不写入”规则和加标签的混合检索两个对照；阶段 1 数出样本量（T006） |
| 主模型与判分器老化 | Qwen3-8B 发布于 2025 年 4 月；判分器快照会下线 | 在阶段 1 选定当代小模型和判分器快照；测量判分器与官方判分器的一致率；主要结论在较新模型上重复 |
| 词表与模板过拟合开发历史 | 核心词表、视图模板和提示都在 2 条 LoCoMo 开发历史上冻结 | 报告留出历史上的谓词未命中率和视图命中率；模板与词表同时在受控序列和 LongMemEval 的开发历史上检查；过拟合明显时扩大开发集并重新切分，在预注册之前完成 |
| 人工标注超支 | 图质量的召回标注需要穷举一段消息里的全部声明 | 只在抽样片段上做；工期与人时见 9.4 节；超支时先缩减图质量标注 |
| 基准标签噪声与判分器偏宽 | LoCoMo 金标有误；常用判分器接受含糊的错误答案 | 双口径报告；判分器负对照；固定回答提示；不确定性分来源报告 |
| 外部基线被跑弱 | Graphiti 在小模型下的分数在文献中差别很大 | 公布适配方式、版本与失败率；保留原生骨干一行；原生表与同骨干表分开 |
| 标准尚未稳定 | RDF 1.2 与 SPARQL 1.2 还不是正式推荐标准，引擎支持不齐 | 模型定义一次，给 RDF 1.2 和 RDF 1.1 两种序列化；查询按 RDF 1.1 可执行 |
| 数据许可限制 | LoCoMo 为 CC BY-NC 4.0；HaluMem 禁止演绎 | 只发布切分清单、脚本与标注差异的指针，不再分发改注数据 |

### 11.4 必须核实的事项

前六项属于阶段 0，在其他工作开始之前完成。

- MemShift 附录中作用域键的定义，以及它与声明模式级依赖的差别。这是最大的新颖性风险。
- Martin 等（2010）的确切规则：是否处理 OPTIONAL 与 FILTER，插入与删除是否同等对待，是否有正确性引理。它决定 3.4 节命题的措辞。
- Tether 全文后三分之二的内容，尤其是 token 成本与真实数据回放部分。
- “把见证或证据的变化单列为一级过期”是否已有先例：针对“来源或谱系的增量维护”做一次专门检索。

- StateMem 与 StateGraph 的全文：它们的失效是否沿已消费的记录。读完之后才写入 2.1 节“派生记忆的级联失效”一行。
