### Dependency mechanisms compared with claim-pattern dependencies

Claim-pattern dependencies (plan sections 3.3, 3.4, 5.4): the compiler derives every claim pattern of a view's query, including patterns inside negation and aggregation, with the pattern's constants, its attribution constraint and filters local to the pattern. Each new claim, attribution, evidence link or supersession event is matched against these patterns at write time; any match marks the view. Staleness has two levels, answer and citation.

**Verdict.** No work compared here derives the dependency from an analysis of the defining query, matches each inserted fact against patterns with constants and local filters, or includes patterns inside negation and aggregation. MemShift's scope key is the closest: it catches records entering a definition's range, but the range is hand-coded per definition, has no per-entity constants, ignores aggregates and thresholds, fires on any field revision in range and is recomputed at checkpoints rather than matched per write. Claim-pattern granularity is therefore finer than every agent-memory key found. It is not new outside agent memory: Martin et al. (next subsection) invalidate cached SPARQL results, and application objects rendered from them, by matching each changed triple against the query's triple patterns, and prove the rule sound. A claim pattern is that rule applied to a reified claim with an attribution constraint. The scope key also catches changes caused only by the clock (window exits); plan section 3.3 excludes read-time-relative windows from persisted views, so this case does not arise in this plan.

Note on MemShift Table 9(a), 79.0% is the share of definition item-times re-derived after a deletion, not the share of unchanged items invalidated (52.3%).

### Martin, Unbehauen and Auer (2010)

Improving the Performance of Semantic Web Applications with SPARQL Query Caching. ESWC 2010, LNCS 6089, pp. 304–318, doi 10.1007/978-3-642-13489-0_21. Read in full from the publisher PDF on 2026-11-23; page numbers are the printed LNCS pages.

- **Rule.** "A query result is cached as long as updated triples do not match any of the triple patterns comprised by the graph pattern. Once an updated triple matches any of the triple patterns, the corresponding cache object is invalidated" (§1, p305). Triple patterns are stored with "Variables in the triple patterns ... represented as NULL values" (§4, p309); the invalidating SQL matches each position as `(subject = s OR subject IS NULL)` and so on, restricted to the query's graph IRIs (§4.3, p311). Matching is per pattern: joins, repeated variables and FILTER constants are not used to narrow it.
- **OPTIONAL and FILTER.** The formal fragment is AND, OPT, UNION and FILTER over simple RDF with set semantics, with OPT defined through the difference operator (Definition 1, pp306–307). The proof covers OPT and UNION by composition of join, union and difference, and FILTER by "If [[P1]]D = [[P1]]D+ ..., then the set of solutions for the filter clause stay the same" (proof (b), p308). OPTIONAL patterns are indexed like mandatory ones (Listing 1.1 and Table 1, p310). FILTER conditions are not analysed for invalidation; "the evaluation of SPARQL filter conditions" is named as future work for cache reuse (§7, p317). Aggregates, MINUS and NOT EXISTS are outside the fragment (the paper predates SPARQL 1.1), but OPT already contributes a non-monotone difference, so the soundness argument does not rely on monotonicity.
- **Insertions and deletions.** Treated alike: "Ω is also the set of all solutions for D+ = D ∪ {t} and D− = D \ {t}" (Proposition 1, p307); "When a certain triple is inserted (or deleted) ... we have to invalidate all SPARQL queries which contain a triple pattern matching the inserted (or deleted) triple" (§4.3, p310). The BSBM update dimension uses insertions only (5 to 8 statements per insert, §5.1, p313).
- **Correctness lemma.** Yes. "Proposition 1 (Graph pattern solution invariance). If Ω is the set of all solutions for the graph pattern P with respect to a dataset D and for a triple t there exists no mapping μ from query variables to RDF terms such that t ∈ μ(P), then Ω is also the set of all solutions for D+ = D ∪ {t} and D− = D \ {t}" (§2.2, p307), proved by (a) the triple-pattern case and (b) compositionality of the algebra (pp307–308). It is a soundness statement for one triple; there is no exactness condition and no discussion of over-invalidation. The conclusion states that "the cache never contains outdated cache objects" (§7, p317).
- **Derived objects.** Compound application objects, for example HTML fragments of a page, are associated with "all of the cached query results they depend on" and invalidated "when any of the associated query results change" (§1, p305; §4.2, p310). This is a precedent for invalidating a rendered artifact through the patterns of the queries it was built from; there is no evidence or citation level.
- **Evaluation.** BSBM with Pareto-distributed parameters and an update dimension (one insert per 100, 10 or 1 query mixes), Erfurt (PHP) and a stand-alone Java proxy over Virtuoso; and the Vakantieland application with four usage scenarios, two of which update labels and one adds a new point of interest (§5, pp311–315). No count of unnecessary invalidations is reported.

The Erfurt implementation (branch `develop`, commit `cafb3a4caef01db9cb6dddf97929f7fc34c5477c`, `library/Erfurt/Cache/Backend/QueryCache/Database.php`, `invalidate`) matches the paper and adds one behaviour: above 20 changed statements all cached queries of the graph are cleared.

Consequence for this plan. Pattern-level invalidation of a cached query result and of objects rendered from it, with a soundness proposition proved by compositionality that already covers a non-monotone operator (OPT) and both insertions and deletions, is prior art. What the paper does not contain: NOT EXISTS, counting and latest-state selection; reads parameterised by a cut-off version; matching units larger than one triple (reified claims with attribution constraints); filters local to a pattern; exactness conditions; and any level of staleness besides the result.

### Search records

Both searches were run on 2026-11-23 with a web search tool; the full query log is in `$PROJECT_ROOT/runs/T011/artifacts/reading/search/query-log.txt`.

**Search A: a change of witnesses or evidence as its own level of staleness (incremental maintenance of provenance, lineage and citations).**

Queries: `Green Karvounarakis Ives Tannen "Update Exchange with Mappings and Provenance" incremental maintenance provenance deletion`; `RDA recommendation dynamic data citation timestamped query result set hash re-execute`; `Wu Alawini Davidson Silvello "Data Citation: Giving Credit where Credit is Due" SIGMOD 2018 citation views`; `incremental maintenance of provenance semirings view maintenance provenance changes answer unchanged`; `Liu Taylor Zhou Ives Loo "absorption provenance" recursive views maintenance ICDE`; `Trio ULDB lineage maintenance under updates Widom "lineage" deletions data modifications`; `citation of evolving data query result citation changes versioned database Buneman Davidson citation views maintenance`; `Buneman Silvello "rule-based citation system for structured and evolving datasets" versioned citation`; `Yinjun Wu Davidson data citation views "covering" rewriting provenance polynomial citation version database update`.

Found:

- Green, Karvounarakis, Ives and Tannen, Update Exchange with Mappings and Provenance, VLDB 2007 (section 4 read): provenance relations are maintained with their own deltas; on deletion a tuple whose derivations shrink is re-checked and can survive, so provenance changes while the tuple stays. This case is implicit and is not named or exposed as a staleness level.
- Liu, Taylor, Zhou, Ives and Loo, absorption provenance, ICDE 2009 / TKDE 2010 (technical report read in a targeted way): "If the provenance has indeed changed despite absorption, u gets propagated to the next operator, annotated with provenance deltaPv". The closest operational precedent: a provenance-only change is detected and propagated as its own event. Its purpose is cheaper deletion, not current citations.
- RDA Working Group on Data Citation, Precise, Actionable Reference to Dynamic Data, revision of 2025-04-04 (read in full): timestamped queries, a result-set checksum (R7), re-execution against the current state with a new identifier "if the result set differs" (R4, R11). Direct precedent for read-time re-query with fingerprints, at one level (the result set).
- Data citation by citation views (Davidson et al., CIDR 2017; Wu et al., SIGMOD 2018; ProvCite, VLDB 2019; Buneman and Silvello, 2010): citations built from why- and where-provenance by query rewriting; abstract level only (Wu et al. 2018 could not be opened); nothing found on maintaining citations under updates.
- Trio / ULDB: lineage named as a way to propagate updates to derived data (vision slides); no maintenance algorithm found.

Result: partial precedent. Provenance-only changes are maintained as such in Datalog provenance systems, and result-set fingerprints are standard in dynamic data citation, but no work found defines "answers unchanged, witnesses or evidence changed" as a staleness level of a derived artifact or repairs citations from it.

Found:

- Enzyme, incremental view maintenance at Databricks, arXiv 2603.27775 (read in a targeted way): non-deterministic functions, including AI functions, fall back to complete recomputation.
- Shankar and Parameswaran, Motion, SIGMOD 2024 demo (abstract): prompts as views over unstructured data under a weak consistency model; no staleness criterion.
- SemReuse, arXiv 2610.16035 (abstract): reuse of cached natural-language views across related queries; not about base-data updates.
- FreshCache, arXiv 2607.04281 (search snippet): freshness-aware semantic caching with a learned risk model and content hashes. "CacheSense" was not found under that name.
- LOTUS, Palimpzest, DocETL, ZenDB, ThalamusDB, Galois, UQE, CAESURA, SUQL (snippets): query optimisation and cost per query; no handling of updates found.

Result: nothing found that maintains or invalidates LLM-derived views under base-data updates at query-pattern granularity or with an answer-versus-citation criterion. Several items were read only at abstract or snippet level, which is weak evidence of absence.
